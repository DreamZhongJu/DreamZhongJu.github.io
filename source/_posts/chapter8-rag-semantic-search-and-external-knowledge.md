RAG（Retrieval-Augmented Generation，检索增强生成）让模型在回答时访问外部资料：先检索，再将证据放进上下文，最后生成回答。它的关键不在“给 LLM 接个向量数据库”，而在于形成可追溯的证据链，并分别优化检索、上下文构造和回答生成。

## 一、RAG 解决什么，不能解决什么

LLM 的参数中包含从训练数据中压缩得到的统计规律，但它不是一个可实时更新、可逐条溯源的数据库。面对私有文档、最新规则、具体项目资料或长尾专业知识，仅依靠参数回答很容易遗漏、过时或编造细节。

```text
用户问题
  → 检索外部知识库中的候选片段
  → 选择和组织证据
  → 将证据、问题和回答规则写入 Prompt
  → LLM 生成答案与引用
```

这种基于证据的回答常被称为 grounded generation。它能让回答有可检查的来源，却不自动保证正确：若没有召回关键资料、资料本身错误、上下文被截断，或模型无视证据继续补全，最终仍可能产生错误答案。

## 二、语义搜索：从词面匹配到向量相似性

关键词检索擅长匹配确切术语、编号、API 名称和代码变量，但会错过词面不同、语义相近的表述：

```text
查询：汽车续航
文档：新能源汽车一次充电可行驶 500 公里
```

Dense Retrieval（稠密检索）将查询与文档编码为同一向量空间中的向量，再按相似度搜索：

<div class="attention-formula" role="math">score(query, document) = cosine(embedding(query), embedding(document))</div>

Embedding 能让“机器翻译模型”和“神经机器翻译系统”这类不同措辞更容易相遇，但语义相似不总等于问题相关。一个向量模型可能把主题接近、却没有回答用户所需时间、版本或条件的文档排在前面。

## 三、Chunk：检索质量首先取决于知识如何切分

直接为一整本手册、一篇百页论文生成一个向量，会把背景、方法、实验和结论混成一个表示；查询只能命中文档，难以命中所需证据。RAG 通常先将文档切成 chunk：

```text
文档 → 按标题、段落或语义边界切分 → chunk
     → 每个 chunk 保存向量、原文、来源、位置和元数据
```

切分存在实际权衡：

| Chunk 策略 | 优点 | 风险 |
| --- | --- | --- |
| 固定长度 | 简单、吞吐稳定 | 容易切断句子、表格或代码块 |
| 段落/标题切分 | 语义边界更自然 | 块大小不均，过长段落仍需处理 |
| 递归切分 | 在结构与长度间折中 | 需要为不同文档类型调规则 |
| 语义切分 | 可将主题突变处作为边界 | 计算更贵，边界不一定稳定 |

Overlap 能减少信息刚好被切断的情况，但过大重叠会造成重复召回、浪费上下文。更重要的是保存 `document_id`、页码或标题路径、更新时间、权限和版本：这些元数据既用于过滤，也用于让引用能回到原文。

## 四、Retriever 与 Reranker：召回和精排是两种目标

第一阶段 Retriever 的目标是从大量语料中快速找出“不要漏掉”的候选。它可以是向量搜索、BM25 或混合索引，通常取较大的 top-k。

第二阶段 Reranker 对“查询—候选文本”成对计算相关性，成本高但排序更精细，通常只处理第一阶段的几十到几百条候选：

```text
Query → Retriever（高召回）→ top 100 candidates
      → Reranker（高精度）→ top 5 evidence chunks
      → Context builder → LLM
```

不要用“向量检索返回第一名”代替整个检索系统。Retriever 关注召回率，Reranker 关注前排质量；两者的 top-k、延迟和成本应按语料规模、问题复杂度和上下文预算共同调整。

## 五、Hybrid Search：把精确匹配和语义匹配放在一起

Embedding 检索善于同义改写和概念相近，BM25 等稀疏检索善于精确 token。对论文编号、函数名、错误码、专有名词和日期，关键词往往不可替代。

Hybrid Search 并行获得两路候选，再用加权、归一化或 Reciprocal Rank Fusion（RRF）融合排名：

```text
关键词检索 ─┐
             ├→ 融合候选 → Reranker → 最终证据
向量检索 ───┘
```

没有放之四海皆准的融合权重。应从真实查询集出发，观察“关键文档有没有被召回”“最终前几条是否真正回答问题”，而不是只看某一路离线分数。

## 六、查询不是总能直接拿去检索

用户提问常包含指代、省略、多个子问题或聊天语气。查询增强应帮助检索理解需求，而不能偷偷改变用户意图。

### Query Rewrite

将含混的原问题改写为适合检索的独立查询。例如需要先结合会话历史消解“它”“那个方案”等指代。改写结果应保留原问题，方便审计和回退。

### Multi-query

为同一问题生成若干互补表述或子查询，合并候选。它能提高召回，但也会增加噪声、调用次数和重复证据，需要去重和明确预算。

### Multi-hop Retrieval

某些问题的第二步查询依赖第一步事实。比如先确定某公司在某年的主体信息，再查询该主体的产品或财报。多跳系统需要把每步证据和中间结论保存下来，避免模型将未经证实的中间猜测当作下一跳事实。

### Agentic RAG

当模型可根据证据决定是否继续检索、选择数据源、比较结果或调用数据库时，RAG 进入 Agent 工作流。它提高灵活性，也要求工具契约、调用预算、停止条件和结果验证；“多搜几次”本身不是质量保证。

## 七、上下文构造：检索到不等于模型能有效使用

最终 Prompt 应清楚分隔系统规则、用户问题和检索证据，并附上来源标识：

```text
规则：只依据提供的资料回答；资料不足时说明无法确定。
资料 [S1]：...
资料 [S2]：...
问题：...
输出：结论，并在每条可核查主张后标注来源。
```

上下文有 token 预算。应删除重复片段、保留标题和来源、在必要时压缩长证据，并防范文档中出现的指令性文本覆盖系统规则。检索结果是“不可信数据”，不能被当作高权限指令执行。

## 八、评测 RAG：答案好看不代表系统好

RAG 至少应分开衡量检索与生成两个层面：

| 层面 | 关注问题 | 示例指标或检查 |
| --- | --- | --- |
| 检索 | 关键证据是否进入候选与前排 | Recall@k、MRR、nDCG、人工相关性标注 |
| 上下文 | 给模型的片段是否覆盖问题且没有明显干扰 | 上下文相关性、重复率、覆盖度 |
| 生成 | 回答是否正确、完整、可用 | 正确性、任务完成度、人工偏好 |
| 依据 | 每项主张是否由引用真正支持 | citation precision、citation recall、faithfulness |

Citation precision 问“给出的引用是否真的支持对应主张”；citation recall 问“答案中需要证据的主张是否都给了支持”。Faithfulness 则关注回答是否忠实于提供上下文。它们都不能由“文本很流畅”代替。

评测集应包含真实高频问题、容易混淆的问题、资料缺失的问题、时间/版本敏感的问题和拒答场景。只在几个容易示例上测试，会掩盖检索漏召回和错误归因。

## 九、RAG、Memory 与 Agent 的边界

RAG 主要从外部知识库取证；Memory 主要管理用户、会话和任务的状态；Agent 则负责在目标驱动下编排检索、数据库、代码等工具。

```text
RAG：   “资料中有什么证据？”
Memory：“此前这个用户或任务发生了什么？”
Agent： “为完成目标，现在该使用什么工具与步骤？”
```

它们可以组合，但不该互相替代。用 RAG 存聊天偏好会混淆主体与权限；用 Memory 当论文数据库又会失去版本、引用和批量更新能力。

## 十、一个可落地的最小 RAG 闭环

```text
1. 解析文档并按结构切 chunk，保存来源和版本
2. 为 chunk 建立向量索引，同时保留关键词索引
3. 对查询执行元数据过滤 + Hybrid Retrieval
4. 对候选做重排序、去重与上下文预算控制
5. 用来源编号将证据装配进回答 Prompt
6. 校验引用、记录检索日志，并用真实问题持续评测
```

RAG 不会让模型重新学习知识；它让模型在当前回答中得到更合适、更可验证的信息来源。系统的上限通常取决于知识库质量、切分策略、召回覆盖、排序质量和验证闭环，而不只是换一个更大的生成模型。
