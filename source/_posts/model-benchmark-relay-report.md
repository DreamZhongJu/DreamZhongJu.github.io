---

## 1. 为什么要做这件事

我在搭一个基于多模型 API 中继的智能体工作流，希望按任务类型（通用 / 编码 / 科研 / 深度推理）自动选模型。动手之前需要回答几个问题：

- 同一模型名在不同中转站通道下，质量、延迟、稳定性差多少？
- "便宜大碗"的模型（0.065x 折扣通道、国产开源模型）到底能不能打？
- 哪些模型只是"纸面很强"，实际用起来根本不可用？

于是我盘点了中转站上 9 个分组、200+ 个模型条目，挑出 15 个候选，设计了一套**真实使用导向**的小型测评。本文记录技术方案、踩坑过程，以及最终——不那么严谨——的排名。

## 2. 技术方案与原理

### 2.1 任务集：模拟真实工作负载，不考"脑筋急转弯"

学术榜单（MMLU、GPQA、LiveCodeBench）测的是"知识上限"，但我要的是"干活的模型"。所以任务全部改造成智能体工作流里真实出现的形态：

| 类目 | 题数 | 考察点示例 | 权重 |
| --- | --- | --- | --- |
| GENERAL | 4 | 长文档总结（11 个数值保真 + 反幻觉 + 强制 JSON） | 0.10 |
| CODING | 7 | Bug 定位、LRU 实现（可机器校验）、科研代码诊断、复杂 Debug | 0.35 |
| RESEARCH | 7 | 方法理解、研究漏洞 critique、审稿（Reviewer 模式） | 0.35 |
| HEAVY_REASONING | 6 | 多假设诊断、路由策略设计、约束优化 | 0.20 |

每个任务都带 **rubric（分维度权重）** 和 **golden_points（金标）**，部分编码题（LRU、重构、异步重试）配了**精确 stdout 自动校验**——让模型跑一段代码，跟期望输出逐行比对。

总分公式：`Overall = 0.35×Coding + 0.35×Research + 0.20×Heavy + 0.10×General`。

### 2.2 执行器：串行 + 退避，绝不并发（教训换来的）

中转站有**账号级并发限制**（`Concurrency limit exceeded for account`），并发一高就 503。所以执行器设计为：

- **串行调用 + 指数退避**（最多重试 2 次，429/5xx/超时均可重试）；
- `temperature=0`（部分推理模型会 400 拒绝 temperature，需自动降级重试）；
- **按类目分配输出预算**：推理模型（DeepSeek 系、Kimi 系）会把 token 大量消耗在 `reasoning_content` 上，所以 GENERAL=4000 / CODING=8000 / RESEARCH=6000 / HEAVY=10000；
- **断点续跑**：每个 `模型×任务×轮次` 一个文件，跑挂了重来不重复劳动。

### 2.3 判分：固定强模型 Judge + 机器校验

- **Judge**：固定一个强模型（Claude Opus 系），只看 rubric 打分，不看模型名、不按文风、长回答不加分、事实错误扣分，输出严格 JSON；
- **机器校验**：exact-stdout 题直接执行 Python 比对，和 Judge 各占 50%；
- 二级 Judge（GPT 系）做一致性抽查。

### 2.4 指标

不止"分数"，路由决策需要四维：

- **质量**：四类目加权总分；
- **稳定性**：首试成功率、重试率、5xx 次数；
- **时延**：mean / median / P95（交互体验的命门）；
- **成本**：优先用 API 返回的真实 `cost_cny`，缺失时标注估算。

最终产出 7 个排行榜：coding / research / heavy / general / overall / value（质量÷成本）/ interactive（0.7×质量 + 0.15×稳定 + 0.15×时延）。

## 3. 过程中翻的车（比结果更有价值）

### 3.1 qwen3.8-max：价值王，但在我的通道上"说不出话"

公开评测里它是性价比之王（据说比 DeepSeek V4 Flash 便宜 345 倍）。但实测：**复杂任务（文档总结、编码诊断）在 2000-2500 输出预算下，50-120 秒后 `content` 为空**——所有预算都烧在了 `reasoning_content` 上，`finish_reason=length`，一个字都没产出。简单任务（"回复 OK"）3.7 秒正常。**推理模型的 reasoning 消耗是隐形成本，评测不烧预算就测不出这个坑。**

### 3.2 Node 的 undici 有 300 秒默认 bodyTimeout

长生成调用在 300 秒整被底层 fetch 掐断（报 AbortError），不是中转站超时、也不是我的代码问题。排查后把调用超时调到了 280 秒并给慢模型加了输出预算上限。

### 3.3 中转站通道抖动是常态

当天：GPT_PLUS_PLUS、GEMINI **整组 503/502**；grok 的 4.20 系列全线宕机；GPT_FLOAT 部分模型 44-80 秒才响应。**"模型行不行"和"今天这个通道行不行"是两件事**——稳定性数据全是单日快照，不可外推。

### 3.4 成本字段不可信

不少响应 `billing_pending: true`、`cost_cny: "0.00000000"`。只有部分通道返回真实账单值（实测 Kimi A1 ≈ 0.03 元/次、A3 ≈ 0.08-0.11 元/次）。

## 4. 排名声明（重点，请务必阅读）

以下是**本机测试结果，通过第三方中转站 renai.uno 测得**，**研究不严谨**，理由如下：

1. **样本极小**：设计了 24 道题 × 15 模型 × 多轮，但中转站当天延迟爆炸（单个调用 230 秒~超时），**只完整跑完了少量任务**；
2. **质量分混合来源**：少部分为直接实测（E），大部分参考 2026-08 的**公开评测/新闻**（W）作补充估计，两者混合后打分；
3. **单日快照**：通道抖动、成本 pending、并发限制都影响数值，任何数字换一天都可能不同；
4. **未完成双 Judge 流程**：Judge 方案设计了，但实际评分被叫停，最终分数未经严格双模型交叉验证；
5. **成本指数是相对估算**，不是精确账单。

**所以：本表只对我自己的路由选型有参考价值，请不要把它当作任何形式的基准测试结果或宣传材料。**

## 5. 我自己的结论（供参考）

- **日常默认**：grok-4.6（0.065x）或 claude-sonnet-5，前者省钱、后者最稳；
- **编码**：常规用 kimi-k2.7-code（实测单次 0.01~0.11 元，质量接近旗舰），硬骨头给 gpt-5.6-sol / claude-opus-4-8，代码审查专项用 Codex；
- **科研**：sonnet-5 走量，顶会级深挖升 opus；
- **深度推理**：opus-5（要钱要质量）或 deepseek-v4-pro（只接受异步等待）；
- **排除**：qwen3.8-max（本通道说不出话）、grok-4.5（同价更差）、gpt-5.5（被覆盖）。
