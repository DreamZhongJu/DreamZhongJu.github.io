聊天模型看起来能“记住”此前的对话，但一次 API 调用结束后，它不会自动把这段对话写回参数，也不会在下一次调用中自动得到历史。所谓 LLM Memory，本质是一套**外部状态管理机制**：保存信息，在合适的时机取回，再把它装配进新的上下文。

## 一、模型本身为何是无状态的

一次自回归生成可以抽象为：

```text
当前输入 token → Transformer 前向传播 → 下一个 token 分布 → 生成输出
```

推理过程会产生 KV Cache 等临时状态，但它通常只服务于当前请求或当前会话的生成加速。请求结束后：

- 模型权重不会因为用户说了一句话而改变；
- 历史输入不会自动成为下一次请求的输入；
- 模型也不会自动区分“长期事实”“刚刚的临时要求”和“已经失效的信息”。

因此，准确的表述不是“LLM 记住了用户”，而是“应用把用户相关的历史重新放进了当前 Prompt”。这和上一章的 Prompt Engineering 是同一件事：通过控制 context 改变模型的输出分布。

## 二、记忆系统的最小闭环

一个可用的 Memory 系统至少包含下面四步：

```text
交互或事件
  → 提取：哪些信息值得保存？
  → 存储：以什么结构、带什么来源与时间保存？
  → 检索：当前问题需要哪几条？
  → 装配：以何种优先级放回 Prompt？
```

这四步缺一不可。只保存不检索，历史永远不会生效；只做向量检索不记录来源和时间，旧事实会污染新回答；把所有记录无差别塞进上下文，又会回到 token 膨胀和注意力稀释的问题。

## 三、短期会话记忆：Buffer、Window 与 Summary

### 1. Conversation Buffer：保留完整记录

最直接的方式是把整段聊天记录一起发送：

```text
Human: 我的研究方向是机器翻译。
AI: 收到。
Human: 我刚才说的研究方向是什么？
```

优点是实现简单、细节完整，也最接近用户看到的对话历史。问题是 token 数随轮次线性增长，最终会触及上下文窗口、增加费用和延迟，并让真正相关的信息被大量闲聊淹没。

### 2. Window Memory：只保留最近若干轮

Window Memory 只保留最近 (k) 轮消息，限制上下文长度。它适合当前任务高度依赖近期操作的场景，例如多轮表单填写或代码修改。但用户在二十轮前说过的长期偏好会自然滑出窗口，因此不能单独承担长期个性化。

### 3. Summary Memory：压缩旧历史

Summary Memory 用摘要替代早期原文：

```text
原始对话 → 摘要器 → “用户是机器翻译方向研究生，偏好 Python/PyTorch。”
```

它能在有限 token 预算中保留整体脉络，但摘要是有损压缩：遗漏的数字、条件、否定和来源很难在之后恢复。更稳妥的做法是保留原始记录作为可追溯底稿，摘要只作为上下文导航或会话压缩层。

| 方式 | 保留内容 | 优势 | 主要风险 |
| --- | --- | --- | --- |
| Buffer | 全部原始对话 | 细节最完整 | token、成本和噪声持续增长 |
| Window | 最近 (k) 轮 | 简单且长度可控 | 旧信息被静默遗忘 |
| Summary | 历史压缩摘要 | 适合长对话 | 细节和条件可能丢失或变形 |

## 四、长期记忆不是“更大的聊天窗口”

长期记忆应该保存相对稳定、未来有用、可归属的信息，例如用户的研究方向、明确的写作偏好、项目约束或已确认的决定。它不应机械地记录每一句闲聊，更不应把模型推测当作用户事实。

典型流程如下：

```text
用户消息 / 工具结果
  → 候选事实提取
  → 去重、冲突与权限检查
  → 持久化存储（内容、来源、时间、置信度、作用域）
  → 当前请求到来时检索相关事实
  → 以“可更新的上下文”而非绝对真相写入 Prompt
```

一条长期记忆至少值得包含：`content`、`subject`、`source`、`created_at`、`updated_at`、`confidence`、`scope` 和 `status`。有这些元数据，系统才能回答“这是谁说的、何时确认、能否用于这个会话、是否已过期”。

## 五、怎样决定写入什么：事实、偏好、事件要分开

不同信息的更新语义不同：

| 类型 | 例子 | 合理的更新策略 |
| --- | --- | --- |
| 稳定事实 | “用户是机器翻译方向研究生” | 保存来源；新信息冲突时要求确认或标记版本 |
| 偏好 | “回答希望先给结论，再给细节” | 可更新，保留最近确认时间 |
| 项目状态 | “博客第七章已发布” | 有生命周期，完成后归档 |
| 临时上下文 | “今天只讨论第六章” | 通常只留在当前会话窗口 |
| 模型推断 | “用户可能喜欢某框架” | 不应直接升级为用户事实 |

这也是长期记忆与简单聊天日志的分水岭：它必须有写入标准和更新规则。高风险或敏感信息应更保守，必要时只在用户明确授权后保存。

## 六、检索与上下文装配：相关不等于应该注入

长期记忆常用关键词、元数据过滤、向量检索或混合检索来召回。向量相似度解决“语义上像不像”，却无法独自解决时间、主体与权限问题。

例如用户问“我现在的研究方向是什么”，应优先取该用户最新且已确认的研究方向；而不是取语义最接近的一条旧聊天摘要。一个较稳健的排序可以综合：

```text
相关性 × 置信度 × 新鲜度 × 作用域匹配 × 来源可靠性
```

装配 Prompt 时还应有预算：把最相关的少量事实、近期窗口、必要的摘要和外部证据按层放入上下文，而不是把所有召回结果都塞进去。注入内容越多，不一定越准确，反而可能出现相互矛盾、注意力分散或提示注入风险。

## 七、冲突、遗忘与可追溯性

记忆会过期，也会冲突。用户先说“我使用 PyTorch”，半年后说“项目已改用 JAX”，系统不应静默覆盖并抹掉历史，更不应同时把两条无说明的事实放入 Prompt。

可采取的策略包括：

- 同一主体和属性出现新值时，将旧值标记为 superseded，并保留时间线；
- 低置信度冲突不自动更新，要求用户确认或等待更多证据；
- 为短期项目状态设置过期时间；
- 支持查询、修正和删除，让用户能看见并控制被保存的信息；
- 对每次读取记录来源，便于追溯某个回答为何带入了某条记忆。

“遗忘”不是系统故障，而是正确的状态治理。没有失效机制的记忆库会越来越像难以清理的聊天垃圾场。

## 八、Memory 与 RAG：都检索，但回答的问题不同

| 维度 | Memory | RAG |
| --- | --- | --- |
| 主要问题 | “此前与这个用户/任务发生了什么？” | “外部资料中有什么证据？” |
| 常见内容 | 偏好、决定、会话状态、项目进度 | 文档、论文、手册、数据库记录 |
| 更新来源 | 对话、行为、工具事件、用户确认 | 知识库同步、文档入库、数据更新 |
| 核心要求 | 主体、时间、权限、冲突处理 | 召回、切分、引用、事实支撑 |

二者可以共用向量索引或数据库，但不应共用一套毫无区分的写入逻辑。把企业文档当作用户记忆会混淆权限和更新方式；把个人偏好混进 RAG 文档库又会让证据来源不清。

## 九、Agent 中的记忆分层

一个实际 Agent 往往需要不止一层状态：

```text
工作记忆：当前任务的消息、计划、工具中间结果
会话记忆：当前对话的近期窗口与摘要
长期记忆：稳定事实、偏好、历史决定
外部知识：RAG 文档、数据库、网页与文件
```

工作记忆追求即时性，长期记忆追求治理和可追溯，外部知识追求证据覆盖。将它们混成一个“memory”字段会让存储、召回和权限规则很快失控。

这与博客中已有的[分层记忆治理实践](/2026/08/10/agent-layered-memory/)相呼应：核心不是给 Agent 加一个向量库，而是为信息定义生命周期、操作语义和预算。

## 十、一个安全可维护的最小方案

对于个人研究助手或轻量 Agent，可以从以下最小闭环起步：

```text
1. 原始对话按会话保存，作为可追溯底稿
2. 只提取高价值、稳定且已明确表达的事实
3. 每条事实保存来源、时间、作用域与状态
4. 用元数据过滤 + 语义检索召回少量候选
5. 在 Prompt 中明确“以下是可能过期的历史信息”
6. 对冲突、删除和外部写入保留人工确认
```

这个方案比“每轮都把聊天全文塞回去”复杂一点，却能避免最常见的三类故障：上下文无限增长、旧事实覆盖新事实、模型臆测污染记忆库。

## 十一、本章总结

```text
LLM 本身无状态
  → 外部系统保存信息
  → 按当前任务检索相关状态
  → 在有限预算内装配进 Prompt
  → 用时间、来源、权限和验证治理其生命周期
```

Memory 让一次性语言生成变成连续交互系统，但它不是“让模型记住一切”。好的记忆系统知道什么该保存、何时该取回、何时应更新或遗忘，以及何时应该让用户重新确认。
