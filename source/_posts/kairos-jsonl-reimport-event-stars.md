## 一、纯文本导出的天花板

上一版管线的输入是聊天软件导出的纯文本:只有昵称和内容,没有发送者 ID。后果是连锁的:

- 抽取器从**别人嘴里的提及**建实体,这些实体天生没有身份锚点,496 个"裸人名"只能靠共现聚类猜马甲,猜完还得请群主本人逐个指认;
- 关系的 `valid_from` 靠窗口日期兜底,"我们参加高考"被标成讨论发生那天;
- 昵称→人的映射没有时间维度,"cherry"到底是谁家的号,数据里根本没答案。

新导出格式一行一条消息,字段是这样的:

```json
{"timestamp": 1654921840000,
 "sender": {"uin": "3473286835", "groupCard": "爱sei",
            "nickname": "Adieu", "remark": "…"},
 "content": {"elements": [{"type": "at", "data": {"uin": "..."}},
                          {"type": "reply", ...}]}}
```

三个字段改变一切:`uin` 是发消息那一刻的铁证身份;`groupCard` 是**当时**的群名片(时序别名原料);`elements` 里 @ 和回复自带对方 uin。顺带说,`remark` 字段是真实姓名,**解析器第一行就把它剥掉**,真名不进图谱不进日志。

## 二、管线设计:让身份在入库那一刻锚死

核心渲染只做一件事——每行消息变成 `『群名片(uin)』 内容`,然后整窗喂给抽取器。抽取器从此知道"谁在说话",自述句的主语不再靠猜。

三类关系三条通道,成本完全不同:

1. **确定性边(零 LLM 成本)**:@ 和回复直接从 elements 生成 `(A)-[艾特]->(B)`、`(A)-[回复]->(B)`,双方 uin 都是结构化的;
2. **LLM 抽取边**:照旧走白名单谓词,但每条关系继承真实时间边界;
3. **后锚定**:抽取结果里的实体名,若与该窗口发言人名片精确匹配,`upsert_entity(name, canonical=f"qq:{uin}")` 直接钉死到 QQ 锚点上。

窗口按自然日切,单窗上限 120 条 / 2800 字符,45 万条消息切成 6,253 窗,三供应商六进程分片吞。

## 三、四个事故复盘

### 事故一:FTS5 影子表,删不得

清库时我顺手对全文索引的影子表(`chunks_fts_data` 等)执行了 DELETE。FTS5 的虚表定义就存在 `chunks_fts_config` 里,删掉之后连 `DROP TABLE` 都会触发 `vtable constructor failed`——虚表构造失败,而 DROP 本身要先实例化它。死锁在 schema 层面。

**修复**:反正四张主表已清空,直接删掉整个 .db 文件重建。教训记下:**FTS 表的清理只有 TRIGGER 或 DROP 全家桶两条路,永远不要绕过虚表直接动影子表**。

### 事故二:慢滴响应吊死线程池

并行化之后吞吐反而掉到 1.4 窗/分。py-spy 被 ptrace 权限挡住(容器默认 seccomp),最后用 `/proc/*/task/*/wchan` 看内核等待点:全部线程挂在 `do_poll`——网络收包等待。根因是 SDK 层 `max_retries=3` 乘上自定义 httpx 客户端的 120 秒超时:遇到"每 119 秒滴一个字节"的服务器,读超时永远不触发,一次调用能烧 8 分钟。

**修复**两层:导入进程强制 `MODEL_MAX_RETRIES=0`;再给每次抽取套硬墙钟:

```python
fut = _HATCH.submit(lambda: extract(text, provider=p))
try:
    return fut.result(timeout=150)   # 墙钟到点即放弃
except FutureTimeout:
    return {"entities": [], "relations": []}
```

被遗弃的线程会在自己的传输超时后自然消亡,不会堆积。这一改,吞吐从 1.4 窗/分回到 10+,并发拉满时冲到 152 窗/分。教训:**对外部 IO 的信任必须以墙钟为单位,而不是对方的心跳**。

### 事故三:检查点互踩

三个分片进程共用一个 checkpoint 文件,各自启动时读入内存、每 10 窗整文件覆写——后写的把先写的全部抹掉,重启后大量窗口重复消耗 LLM 配额。

**修复**:per-shard 文件(`ckpt.s{N}.json`),统计完成度时跨文件取 union。

### 事故四:看门狗的监控盲区

给导入配了守护进程:9 分钟无日志写入或进程缺失就全杀重启。运行几小时后发现有一条车道僵死数小时无人管——因为 freshness 检查只列了前三个日志文件,第 4 条车道成了法外之地,而它的分片没有别人兜底,**那 1,000 多个窗口会静默丢失**。

**修复**:逐车道比对日志 mtime,任一超过 15 分钟无写入即触发重启。上线后第一个巡检周期就精准逮到了那条僵死车道。

## 四、数据自己开口说话

重导完成后,最有意思的不是统计数字,而是这批数据里自动浮现的时代切片:

**年份分布**(抽取窗数):2022 年 849 窗——这是旧管线从未覆盖的史前史, Minecraft 整合包服务器时代;2023 年 1,599 窗是高峰;2024 起稳定在 1,100-1,400 窗/年。

**群名片时序考古**。同一批 uin 在四年半里的名片演化本身就是一部编年史:

```
某成员: 爱sei(2022-06 至今,主力) → 总力战高手 → k奶龙 → 设精高手
        → 大份拌大常 → 居委会(2025-02) → 居委会(暴揍zblyyzxzjsdhrx版)
另一位:  要屯方舟300抽(13/300) → (67/300) → (143/300) → (172/300)
        ← 抽卡保底进度条被此人写在了名片里,时间戳精确到月
```

以前要做"这个号历史上叫过什么"的考证,只能翻聊天记录人肉搜索;现在这是一条 SQL。

**事件星拿到真实时间轴**。n 元超边以事件为中心聚合参与者,这次每个事件都带着数据里长出来的日期:

```
★ 核酸检测 @2022-09-18   四人同测 —— 疫情时代的集体记忆,零人工标注
★ 填志愿   @2022-06-30   高考出分后的志愿填报夜
★ 网课     @2022-09-14   上网课 @2022-12-03
★ 内战     @2023-12-28   组织者+三名参战者
★ 军训     @2023-09-23   12 名参与者,教官也在名单里
★ 考研     @2026-07      八人,含两位真名(已脱敏)
```

注意「军训」的 12 元结构:这是链式超边原理上表达不了的东西——一个事件节点同时挂 12 个人,查询任何一名参与者,整个集体事件一键浮出。而「核酸检测」的日期我从头到尾没有告诉过系统,它是从 45 万条消息的证据里自己长出来的。

## 六、还没做完的

- 抽取器仍会把部分被提及者建成裸实体,后续窗口发言人到场时会自动补锚,但永远潜水的提及对象只能保持诚实的不确定;
- 共指注册表的别名合并存在一条短路路径(裸实体已存在时不走注册表解析),目前用清扫脚本兜底,根治要改 `upsert_entity` 的查找顺序;
- 旧库的手工修正(玩笑降级、日期钉扎)随清库丢失,新数据靠真实时间戳天然规避了大半,但"玩笑半价"逻辑值得在新库上重跑一遍。
