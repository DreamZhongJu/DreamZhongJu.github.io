## TL;DR

我报名了 OSPP（开源软件供应链点亮计划）2026 的一个课题：**基于 Agent 实现财报采集分析与可追溯研究**。导师通过邮件提出三项材料要求：① 简历 PDF；② 可演示的财报分析效果 demo；③ FinGLM 数据集（11588 份上市公司年报 PDF）。

我用三周把技术做得很扎实：复现并定位了上游脚本的三个经典抽取错误，重写了带页级定位和 17 字段来源元数据的抽取器，会计恒等式校验误差为 0，8 项定位可复现全部通过，还合入了一个上游 PR。**结果还是被拒了。**

复盘下来的核心原因不是"做得不够"，而是**"交付的时机和形式"**：导师要的三样材料，只有简历有产出文件，demo 停留在本地截图，数据集没有真正处理，而给导师的回复始终是草稿。在"短窗口、多候选人"的评估里，这等于放弃。

## 一、背景：我为什么报这个课题

我一直在做知识图谱与可追溯性的东西：GraphRAG、证据链问答、来源可复现。这个课题的"公开资料发现 → PDF 解析 → 指标抽取 → 来源追踪 → 引用报告"链路，几乎是我技术栈的正中心。导师又是知名开源项目 DB-GPT 的成员，课题就是给这个项目加一个可追溯的财报分析技能。

当时我的想法很朴素：**把技术做扎实，材料自然有说服力。**

## 二、我做了什么：这条线其实很扎实

### 2.1 复现上游脚本的真实 bug

DB-GPT 仓库里已有一个 `financial-report-analyzer` skill，但它的抽取脚本用**全文正则第一个命中**来取值。我拿样例年报一验证，立刻复现出三个经典错误：

- `营业收入` 在一份年报正文里出现 29 次、跨 17 页，脚本取到的是**第一个命中**，而不是合并利润表里的那一个；
- `流动负债合计` 被当成 `负债合计` 读走；
- 分行业（分部）表格里的营业收入被当成营业成本。

这三个错误对"可追溯财报分析"来说是致命的：**数字本身都是错的。**

### 2.2 重写抽取器：页级定位 + 精确匹配 + 来源元数据

我重写了 `extract_financials_v2.py`，关键改动：

- **页级表格定位**：用"母公司报表页"作为边界反推"合并报表页"——这正好是合并报表与母公司报表口径隔离的核心难点；
- **精确行标签匹配**：整行精确匹配，拒绝子串匹配（子串匹配正是误读的根源）；
- **17 字段来源元数据**：页码、表索引、行标签、表名、报表口径、原始值、抽取方式、来源 URL、内容哈希、解析器版本、抽取时间、币种、计量单位、报告期、报表类型……每个数字都能回答"从哪来、怎么来的"；
- **会计恒等式校验**：资产 = 负债 + 权益、毛利 = 营收 − 成本，两份样例误差都是 0；
- **定位可复现验证**：用记录的页/表/行重新抽取，8/8 全部命中同一个值。

前端还做了一个可追溯对比报告（HTML）：LLM 摘要、核心指标对比、恒等式校验结果、定位验证结果、完整来源明细、证据 JSON 引用，六个模块一屏展示。

### 2.3 开源线：这条线其实在变好

- PR **#3189** 合入 DB-GPT（大型 Agent 消息在 MySQL 上的存储修复）；
- PR **#3187** 获得核心维护者"实现看起来正确"的 review，剩两个确认问题我逐一回复补了验证；
- PR **#3188** 第二轮 review 回应 + 真机端到端验证。

有一段时间导师不回复，我一度怀疑是不是被放弃了，于是去翻了仓库最近被合并的 PR：**干净的小 PR 从开到合普遍只要 0.8~2.4 天，全部 squash merge，核心维护者亲手合。** 仓库活跃度完全正常，"被放弃"这个担心并不成立。

## 三、失败一：申请被拒（结果）

导师一直没有回复。结果公布，未入选。

回头看时间线：我把大量精力花在"把 demo 和验证打磨得更完美"上，反复核对细节；而导师要的三样材料里，**demo 停留在本地截图，FinGLM 数据集没有真正处理，给导师的回复始终没有发出**。到结果公布那一天，我才意识到：我做了很多，但**没有任何东西真正递到对方眼前**。

## 四、失败二：交付的失败（原因）

这才是真正的失败点，而且它是独立于结果的一段失败经历：

1. **没有"可演示"的形态**。导师要的是"可演示的财报分析效果"，我给的是本地 PNG 截图 + 跑在 `localhost` 的服务。截图 ≠ 可演示——对方看不到、点不开、跑不了。真正合格的交付物是：≤3 分钟的录屏、一个部署好的 URL、或者一套可运行的极简环境。
2. **没有及时的送达**。评估是"短窗口 + 多候选人"的赛制，导师同一封邮件发给所有申请者，比的就是谁快、谁直接。我花三周打磨，而不是收到需求后 48 小时内先回一版——在对方视角里，这就是响应慢。
3. **三样材料缺一**。FinGLM 的 11588 份年报 PDF 正是课题核心语料，把它处理出一个子集样例（哪怕 20 份）是"我真的准备投入"的最直接证明，我没有做。

**打磨到完美的顺序错了：在评估场景里，速度 > 完美度，可直达 > 精致度。**

## 五、为什么会被拒：五条归因

按证据强度排序（前两条基本可以坐实，后三条是诚实评估）：

| # | 归因 | 说明 |
|---|------|------|
| 1 | **交付时机** | 材料没在窗口内及时送达，等于默认放弃 |
| 2 | **可演示形式** | 本地截图/localhost ≠ 可点开可运行的 demo |
| 3 | **材料完整度** | FinGLM 数据集从未真正处理，三样要求缺一 |
| 4 | **背景档位** | 对手池里有上届 OSPP 入选者、985 硕士、申请前已交付完整原型的选手；我当时的公开可核验资产只有一个非财报方向的小 PR |
| 5 | **申请书形态** | 纯文字长文档，没有架构图/流程图/结果截图，评审快速扫读时吃亏；而且我把验证出的硬结果（0 误差、8/8 可复现）没有实时写进申请书 |

## 六、旁证：同课题的另一条失败路线

申请期间我在同一个仓库里看到另一个申请者做了类似的事：把整套"财报采集 → 解析 → 抽取 → 来源追踪 → 引用报告"模块（好几百个文件的大模块）一次性提交成 PR，**第二天就被维护者关闭，没有任何人工评论**。

这条信息对我很有价值：开源社区**不吞陌生人的大块功能 dump**，"小步修复 → 建立信任 → 逐步扩大"才是合入路径。我的小 PR 能合入、他的大模块被秒关，正好互相印证了这条社区规则——也提醒我，下次如果真要为项目贡献整块能力，应该先拆成阶段性的小 PR 逐步合入，而不是憋一个大招。

## 七、失去的与没失去的

**失去的**：这一个课题的名额、与这位导师合作的机会。仅此而已。

**没失去的**：

- PR 合入是**永久**的，写在公开历史上；
- 页级定位 + 精确匹配 + 17 字段来源元数据这套抽取代码，以及全部验证数据（恒等式 0 误差、8/8 可复现），是实打实的技术资产，换任何项目都能复用；
- 我验证了"页级定位修复"是**真实存在**的 bug——全文正则首搜的错误在任意 PDF 财报解析里都会出现，这个判断本身有长期价值。

## 八、给下一次的清单（可执行）

1. **收到评估方的要求后 48 小时内回第一版**，先送达、再打磨；打磨永远放在交付之后。
2. **交付物永远做成对方能直接看到的形态**：≤180s 录屏、部署好的 URL、可运行的最小环境，三选一。
3. **验证结果（数字）实时写进申请书**，边做边更新，而不是最后补。
4. **社区贡献从小而聚焦的修复开始**，不一次性 dump 大模块；整块能力拆成阶段性小 PR 逐步进。
5. **区分"做得完美"和"交付及时"**——在评估场景里，后者是评分项，前者只是我自己的心理安慰。

## 后记：为什么要把它写下来

这类失败很少有人完整记录——网上大量是"我如何拿下 OSPP"的成功学，很少见到"材料都做好了还是被拒"的全过程。失败里最有价值的部分恰恰是那些**当时以为对、事后看是错的决策**：把打磨放在送达之前、把截图当作 demo、把"做得够不够"当成核心问题而不是"递没递到"。

被拒不是零分，它只是明确告诉我：这个窗口、这种方式不行。下一窗口换个方式再来。

如果这篇复盘能让你少走一点弯路，就够了。
