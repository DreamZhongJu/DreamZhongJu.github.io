## TL;DR

我报名了 OSPP（开源软件供应链点亮计划）2026 的一个课题：**基于 Agent 实现财报采集分析与可追溯研究**。导师通过邮件提出三项材料要求：① 简历 PDF；② 可演示的财报分析效果 demo；③ FinGLM 数据集（11588 份上市公司年报 PDF）。

之后的三周我很忙：复现并定位了上游脚本的三个经典抽取错误，重写了带页级定位和 17 字段来源元数据的抽取器，会计恒等式校验误差为 0，8 项定位可复现全部通过，还合入了一个上游 PR。**结果被拒了。**

复盘下来，真正的失败点不是"做得不够"，甚至主要也不是"做得慢"，而是：**从头到尾我没有完成哪怕一次真实的沟通。** 导师的要求我其实没有完全看懂，但一句话都没有追问；回复邮件我不会组织语言，让 AI 替我写，写得确实比我好——可每一版都让我觉得"这不是我说的话"，发信就变成心理负担，永远停在草稿箱；"可演示的财报分析效果"，我理解成了"把分析结果做成一份漂亮的 HTML 报告"，而它真正想验证的是**这个课题能不能在你的手里跑起来、给我看到**。

技术的部分很扎实，可它没有一个字节到达过对方的眼睛。

## 一、背景：我为什么报这个课题

我一直在做知识图谱与可追溯性的东西：GraphRAG、证据链问答、来源可复现。这个课题的"公开资料发现 → PDF 解析 → 指标抽取 → 来源追踪 → 引用报告"链路，几乎是我技术栈的正中心。导师来自知名开源项目 DB-GPT，课题就是给这个项目加一个可追溯的财报分析技能。

我当时想得很简单：**把技术做扎实，材料自然有说服力。**

我不知道的是，这个课题对我的最大考验根本不在代码里，而在我和导师之间的那几封邮件里。

## 二、我做了什么：这条线其实很扎实

### 2.1 复现上游脚本的真实 bug

DB-GPT 仓库里已有一个 `financial-report-analyzer` skill，但它的抽取脚本用**全文正则第一个命中**来取值。我拿样例年报一验证，立刻复现出三个经典错误：

- `营业收入` 在一份年报正文里出现 29 次、跨 17 页，脚本取到的是**第一个命中**，而不是合并利润表里的那一个；
- `流动负债合计` 被当成 `负债合计` 读走；
- 分行业（分部）表格里的营业收入被当成营业成本。

这三个错误对"可追溯财报分析"来说是致命的：**数字本身都是错的。**

### 2.2 重写抽取器：页级定位 + 精确匹配 + 来源元数据

我重写了 `extract_financials_v2.py`，关键改动：

- **页级表格定位**：用"母公司报表页"作为边界反推"合并报表页"——这正是合并报表与母公司报表口径隔离的核心难点；
- **精确行标签匹配**：整行精确匹配，拒绝子串匹配（子串匹配正是误读的根源）；
- **17 字段来源元数据**：页码、表索引、行标签、表名、报表口径、原始值、抽取方式、来源 URL、内容哈希、解析器版本、抽取时间、币种、计量单位、报告期、报表类型……每个数字都能回答"从哪来、怎么来的"；
- **会计恒等式校验**：资产 = 负债 + 权益、毛利 = 营收 − 成本，两份样例误差都是 0；
- **定位可复现验证**：用记录的页/表/行重新抽取，8/8 全部命中同一个值。

前端还做了一个可追溯对比报告（HTML）：LLM 摘要、核心指标对比、恒等式校验结果、定位验证结果、完整来源明细、证据 JSON 引用，六个模块一屏展示。

### 2.3 开源线：这条线其实在变好

- PR **#3189** 合入 DB-GPT（大型 Agent 消息在 MySQL 上的存储修复）；
- PR **#3187** 获得核心维护者"实现看起来正确"的 review，剩两个确认问题我逐一回复补了验证；
- PR **#3188** 第二轮 review 回应 + 真机端到端验证。

后来我去翻了仓库最近被合并的 PR：干净的小 PR 从开到合普遍只要 0.8~2.4 天，全部 squash merge，核心维护者亲手合。仓库活跃度完全正常——**代码上的协作我从头到尾都是顺畅的，唯独最关键的邮件往来停摆了。**

## 三、失败一：申请被拒（结果）

导师一直没有回复。结果公布，未入选。

## 四、失败二：一场从未发生的对话（原因）

这才是真正的失败点。它不是一个动作做错了，而是**一整条沟通链路，每一步都断开了**。

### 4.1 "可演示的效果"，我理解错了

现在我可以给出这个词的正确翻译了。"可演示的财报分析效果"，评审语境下想验证的是：**这个课题能不能做成、而且能在你的手里当场跑出来**——比如在真实年报上把"解析 → 抽取 → 校验 → 带引用的报告"完整链路跑一遍，用一段录屏或一个我能打开的地址给导师看。

而我交出来的想象中的答案是：一份两家公司的**静态 HTML 对比报告**。它是一份"成品"，不是一场"演示"；是给最终读者看的报告页面，而不是给评审看的能力证明。更要命的是，即便如此我也拿不准这样算不算"可演示"——这种拿不准本身就是信号：我对要求的理解从第一天起就没有和导师对齐过。

公平地说一句：那份 HTML 的内容并不蠢——17 字段的证据链、恒等式零误差、可复现性验证都是真的硬货。蠢的不是它，蠢的是我给它安排的角色（充当"效果演示"），以及它最终的命运（从未被任何人看到）。

### 4.2 我为什么不去问

回头看，整场申请里有三个只要问出口就能救回来的澄清问题：

1. "demo 您期望的形式是什么？录屏、在线地址，还是我带您现场跑一遍？"
2. "数据集这边需要我先在子集上跑通给您看吗？还是只想确认我有处理它的条件？"
3. "在正式截止之前，除了这三样，您还希望分阶段收到什么？"

这三个问题全都简单得像废话。但当时的我有更真实的顾虑：**怕显得不懂行、怕麻烦导师、默认"准确理解要求是申请人自己的事"。** 于是我选择了另一条路——自己猜，猜完照着自己猜的方向闷头做。越埋头做，越没有机会发现自己猜错了方向。

现在我会把这当成铁律记下来：**面对一个含糊的要求，48 小时内该回的不是作品，是提问。** 提澄清问题从来不会显得蠢，瞎猜三个星期然后沉默才会。

### 4.3 AI 代笔：我把自己弄丢了

第三段最难写，但也最重要。

我清楚自己的短板：结构化写作、把话说得体面，这些我不擅长。所以回复邮件我全程让 AI 来写。事实是它写得确实比我好——逻辑清楚、语气恰当、看起来无懈可击。

但每一次读完 AI 生成的版本，我心里都会冒出同一个念头：**"这不像我说的话。"**

后果不是信写不出来，而是信发不出去：每一版我都想再改一改，改得更"稳"、更"专业"、更不像我会说出错话的样子；随之而来的是新的焦虑——万一被看出来这是 AI 写的呢？万一信里的某个说法我其实答不上来呢？**发信这个动作被我无限期推迟了，而推迟的理由包装起来叫"还没打磨好"。**

这里必须诚实地切割一件事：用 AI 辅助写作本身没有错，几乎所有 review 过我开源 PR 的维护者都见惯了得体的英文 issue。错的是我把顺序弄反了——我把"自己想明白 + 用自己的话说出来"这道工序整个外包了出去，AI 再漂亮也只是替身，替身是没有勇气按下发送键的，因为它不用承担后果。真正该由我完成的部分只有两件：**先想清楚要说什么，再决定要不要说。** 文字润色，永远排在这两件事后面。

下次的正确用法我会写成一条规则贴在桌上：初稿我用最烂的口语写完——就是那种短句加语气词的版本，AI 只允许做语法和排版层面的清理；最后发出去的每一个字，都必须是我敢当面念给导师听的。

## 五、为什么会被拒：五条归因（修正版）

按因果关系的深度排序：

| # | 归因 | 说明 |
|---|------|------|
| 1 | **需求理解错位且未澄清** | "可演示的效果"什么意思，我与导师从头到尾没有对齐过；而澄清的问题一个都没有问出口 |
| 2 | **沟通彻底单向** | 导师视角里我就是持续的沉默：没有进度同步、没有追问、没有半成品求反馈——评估方无从分辨"还在做"和"已经放弃" |
| 3 | **表达外包引发发送瘫痪** | 回复依赖 AI 代笔后不再敢署名发出，所有材料连同草稿一起停在本地 |
| 4 | **交付物角色配错** | 把"能力演示"做成"成品报告"，且无录屏、无公开链接、无一键复现路径 |
| 5 | **材料与对手的客观差距** | FinGLM 数据集从未实际处理；申请书纯文字无图无数据；对手池里有上届入选者、已有完整原型的硕士 |

前四条的共同点值得单独写出来：**它们全部发生在我一个人的脑子里，对方一项也无法感知。** 这是与"技术不行"完全不同的一类失败——它模拟不出任何警告音，直到结果公布才有回响。

## 六、旁证：同课题的另一条失败路线

申请期间我在同一个仓库里看到另一个申请者做了类似的事：把整套"财报采集 → 解析 → 抽取 → 来源追踪 → 引用报告"模块（几百个文件的大模块）一次性提交成 PR，**第二天就被维护者关闭，没有任何人工评论**。

这条信息同样揭示沟通的价值：那次失败的方向刚好和我相反——他是"只交付、不沟通"，我是"只内耗、不交付"。两条路殊途同归地撞在同一个规律上：**开源社区里的协作，本质上是由一次次小而具体的对话组成的。** 只砸一个大模块过来，或者憋着一个完美的 demo 不出手，都跳过了这个规律。

而我在 PR 上的经历恰好反过来：#3189 从提交到合入，中间有三轮真诚的一问一答（维护者确认问题场景、我补真机验证）。**会问、会答、会及时回应，才是这个世界的通用接口。**

## 七、失去的与没失去的

**失去的**：这一个课题的名额、与这位导师合作的机会。仅此而已。

**没失去的**：

- PR 合入是**永久**的，写在公开历史上；
- 页级定位 + 精确匹配 + 17 字段来源元数据这套抽取代码，以及全部验证数据（恒等式 0 误差、8/8 可复现），换任何项目都能复用；
- 那份被我认为"太蠢"的 HTML 报告，内容依然是资产——它只是被放错了用途；
- 以及这份花了被拒代价才买到的教训：**沟通不是锦上添花，它就是事情本身。**

## 八、给下一次的清单（可执行）

1. **收到含糊的要求，48 小时内回的不是作品，是澄清问题**——把我没看懂的词直接拎出来问，"可演示"是三个字的事。
2. **动手前先用三五句话向对方复述理解**："我计划这样做 demo……方向对吗？"拿到一句 yes 再开工，成本三十秒。
3. **邮件初稿必须自己写**，哪怕烂；AI 只许做语法和排版清理；发出的每一个字都要经得起当面朗读。
4. **"可演示"的最低合格线**：≤180 秒录屏、一个公网可访问的地址、或一条可复现命令——三者必有其一，缺一不算演示。
5. **数据集先跑通 10~20 份的子集**，一段真实跑通的输出比任何长期规划都有说服力。
6. **社区贡献从小而聚焦的修复开始**，别一次性 dump 大模块——那份信任是靠一次次小对话攒出来的。

## 后记：为什么要把它写下来

这类失败很少有人完整记录——网上大量是"我如何拿下 OSPP"的成功学，很少有人承认"我看不懂对方要什么，也不敢问，发的邮件是自己都不敢署名的代笔"。

被拒的那一刻我以为输在材料不够完美。几周后复盘才看清：输在那场本可以有来有回的对话，从头到尾就没有开始过。三行笨拙的真话，胜过三千字的完美草稿。

下一窗口，我先学会把话说出口。

如果这篇复盘能让你少走一点弯路，就够了。
