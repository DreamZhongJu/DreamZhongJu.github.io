去年到今年我一直在做一个自托管的飞书研究助手：你在飞书里发一句"最近机器翻译有什么值得关注的进展？"，它会自动检索网页和论文、综合可信来源、给出带来源的回答；你发一个 PDF 说"整理一下"，它会解析、总结，并在你明确同意后才归档。这篇文章复盘它的 Agent 工程部分——为什么用 LangGraph、工具层怎么设计、以及踩过的坑。

## 设计目标

这个项目从一开始就有四个约束：

1. **自托管、私有**：模型密钥、飞书授权、记忆、日志全部由部署者自己持有，不依赖任何外部 SaaS。
2. **让 LLM 决定工具，而不是关键词路由**：业务代码不写"如果包含'论文'就调论文搜索"这种规则。
3. **失败可见、可恢复**：搜索失败、模型超时、飞书接口报错时，要么降级要么明确说明，不能编造。
4. **把"对话、检索、阅读、整理、归档"连成一条可解释的工作流**。

## 分层架构

代码按依赖方向从上到下分六层，低层模块不能导入高层：

```text
飞书事件
  -> Channel Adapter（验签、解析、去重、回复）
  -> Application Service（组装上下文、权限、任务）
  -> LangGraph Agent（模型决策、工具调用循环、结果整合）
  -> Tool Layer（网络、论文、文档/知识库、日程、文件、记忆、MCP）
  -> Infrastructure（DeepSeek、飞书 OpenAPI、SQLite、HTTP）
```

这样做的直接好处是：飞书适配器不需要知道 Agent 内部怎么决策；网页搜索工具也不需要知道飞书消息格式。每个工具只返回一个统一的结构化结果，Agent 根据结果决定重试、换工具还是向用户说明。

## LangGraph 工作流

Agent 核心是一个很简单的图：

```text
START -> agent -> tools -> agent -> ... -> END
```

`agent` 节点把用户问题、会话摘要、相关长期记忆和工具定义交给模型，模型以原生 tool calling 决定调用哪些工具；`tools` 节点（LangGraph 的 `ToolNode`）执行并回填结果，再回到 `agent` 继续推理，直到模型不再请求工具。

几个关键约束：

- **工具轮次上限**：单次请求最多 3 轮工具调用，防止模型陷入循环。
- **会话状态**：用 LangGraph 的 SQLite checkpointer 持久化会话，按用户隔离（`thread_id`）。
- **写操作必须显式确认**：创建文档、归档知识库、创建日程都属于"高风险写工具"，只有用户明确给出指令才执行；批量归档先返回预览和确认码。
- **工具结果要截断、清洗、带来源**，避免超出模型上下文。

## 工具层设计

当前注册了 20 个原生工具，按能力分几组：

- **搜索与阅读**：网页搜索、正文读取、Exa 语义搜索
- **论文**：arXiv / OpenAlex / Semantic Scholar / Hugging Face Papers 检索
- **飞书域**：云文档读取、知识库检索、日程查询、写文档、归档
- **平台内容**：GitHub 检索、YouTube / X / Reddit / B 站
- **记忆**：长期记忆搜索

另外通过 MCP 协议动态接入外部工具（详见另一篇《让 Agent 长出"外挂"》），新工具不需要写代码。

工具统一返回 `ToolResult`：

```python
ToolResult
  tool_name, status, data, sources, error_code, retryable
```

即使失败也要有明确的 `status`、`error_code` 和 `retryable`，Agent 据此决定重试或换工具。

## 踩过的坑

### 1. DeepSeek 偶发返回文本形式的工具调用（DSML）

某些模型在压力下会把工具调用写成文本而不是结构化 JSON。我们做了一个兼容层：解析文本里的 `invoke name="..."` 片段，转成真正的工具调用。这个 fallback 在线上救了不少请求，也提醒我：**不要假设模型永远输出规范格式**。

### 2. 无凭据时模块要能导入

一开始模块顶层直接 `OpenAI(api_key=...)`，一旦没有环境变量整个包都 import 不了，CI 和测试全挂。后来改成凭据为空时不创建客户端、运行到需要模型时再提示缺失，才让"无凭据环境跑全部单测"成为可能。

### 3. 飞书事件要幂等

飞书 WebSocket 可能重推事件，消息处理前先写入 `handled_messages` 表做去重，重复事件直接丢弃。

### 4. 别把上下文塞爆

工具返回的正文可能很长，每个工具结果都要截断和清洗；会话上下文也只保留最近 N 条消息的摘要，而不是全量历史。

## 效果与局限

这个项目让"研究助手"从概念变成了每天在用的工具。它的工程价值在于：分层清晰、失败可见、工具可扩展。局限也很明显：单机自托管没有多租户和横向扩展；检索质量依赖外部接口；Agent 的深度（多步规划、反思）还比较浅——这些是下一步的方向。

如果你也在做类似的 Agent 应用，我最大的建议是：**先把"失败可见"做进去，再谈功能丰富**。一个会诚实说"我没查到"的助手，比一个会编造的助手可靠得多。
