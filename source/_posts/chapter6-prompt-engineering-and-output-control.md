提示工程的目标不是把一句话写得“更像咒语”，而是通过输入设计、任务拆分和输出约束，让一个概率模型以可预测的方式完成任务。真正稳定的 LLM 应用，通常不止有一个 Prompt，还包括上下文装配、解码策略、工具协议和结果校验。

## 一、Prompt 改变的是什么

自回归语言模型在当前上下文 (c) 下，对下一个 token 给出条件分布：

<div class="attention-formula" role="math">P(next token | context)</div>

Prompt 不会在推理时为模型新增知识或修改权重；它改变的是 `context`。因此下面两个请求会诱导出不同的输出分布：

```text
解释 Transformer。

你是一名 NLP 研究员。请从计算图、注意力公式和工程代价三个角度解释
Transformer；用三段文字回答，并指出 KV Cache 的作用。
```

第二个 Prompt 提供了角色、任务范围、评判维度和输出格式。它的价值是减少歧义、激活已有能力、使应用程序更容易处理结果，而不是保证模型不会出错。

## 二、Chat Template：用户看到的文本不一定等于模型看到的输入

聊天模型常把系统消息、用户消息和助手消息按特定模板序列化为特殊 token：

```text
<|system|>
你是一个技术助手。
<|user|>
解释 Attention。
<|assistant|>
```

这个 Chat Template 是模型的输入协议，用于区分角色、提示何处开始生成、标记何处结束。不同模型的模板不相同；如果部署时使用了错误模板，即使用户文字不变，模型也可能把指令、历史或工具结果理解错。应用层应使用模型对应的 tokenizer/template，而不是手工拼接看起来相似的标记。

## 三、解码策略：同一概率分布也能产生不同输出

LM Head 输出的是 logits，经 softmax 转成 token 概率；真正决定选哪个 token 的是解码策略。

### 1. Greedy decoding 与 temperature

Greedy decoding 每一步选择概率最大的 token，结果最可复现，但容易保守、重复。Temperature (T) 会在 softmax 前缩放 logits：

<div class="attention-formula" role="math">P(token) = softmax(logits / T)</div>

较低的 (T) 会让分布更集中，适合固定格式提取、翻译和多数代码任务；较高的 (T) 让低概率候选更有机会被采样，适合发散式写作与方案探索。`temperature = 0` 在很多 API 中近似贪心，但具体行为仍取决于服务实现。

### 2. Top-k 与 top-p

Top-k 只保留概率最高的 (k) 个候选再采样。Top-p（nucleus sampling）则按概率从高到低累加，只保留累计概率刚达到 (p) 的最小候选集。

```text
A: 0.40  B: 0.30  C: 0.20  D: 0.05  E: 0.05
top-p = 0.90 → 只在 A、B、C 中采样
top-k = 3    → 只在 A、B、C 中采样
```

两者不应随意叠到很激进：过度截断会造成输出僵硬或重复。对于可验证的任务，优先降低随机性并把精力放在约束、检索和验证；对于创意任务，再适当提高采样空间。

## 四、Prompt Chain：把复杂目标拆成可检查的中间步骤

一个 Prompt 同时要求“读论文、抽取方法、判断创新性、比较基线、写报告”时，模型必须在同一次生成中承担多种目标。Prompt Chain 将它们拆成阶段，每个阶段都有更明确的输入和可检查的输出：

```text
论文 PDF
  → 提取方法、数据集和指标
  → 对照实验与主张的一致性检查
  → 生成优点、风险与问题清单
  → 写成审稿式摘要
```

拆分的收益包括：中间结果可记录、可重试、可单测，失败位置更明确，也能让不同阶段使用不同模型、不同温度或不同校验器。代价是调用次数、延迟和上下文管理增加，因此应按任务边界拆分，而不是把每一句话都做成一次调用。

RAG 也是典型的链式系统：

```text
问题 → 检索 → 重排序 → 组织证据 → 生成回答 → 引用/事实校验
```

Prompt 只是最后“组织证据 → 生成回答”的接口，不能替代检索质量、来源治理和回答后的验证。

## 五、In-context Learning：用示例临时指定任务

In-context Learning 是把任务示例直接放入当前上下文，让模型模仿输入输出模式。它不执行梯度更新，因此和微调的区别很清楚：

| 方法 | 改变什么 | 影响范围 |
| --- | --- | --- |
| Fine-tuning | 模型权重 | 长期，面向许多后续请求 |
| Zero-shot Prompt | 任务说明 | 只影响当前请求 |
| One-shot / Few-shot | 说明加一到多个示例 | 只影响当前请求，但格式约束更强 |

Few-shot 示例不只是“展示答案”。它在告诉模型标签边界、措辞风格、字段顺序和异常情况应该怎样处理。示例应覆盖容易混淆的边界，并与真实请求保持相同格式；把大量相似示例塞进上下文，反而会消耗 token、引入偏置。

## 六、Chain-of-Thought、自洽性与搜索：给复杂问题更多中间计算

Chain-of-Thought（CoT）让模型先产生中间步骤再给结论。中间 token 会进入后续上下文，因而可以帮助某些多步计算、符号推理和约束规划任务。它不是模型具有“人类式思考”的证据，也不应把生成的推理文字当成可靠的内部因果解释。

Self-Consistency 的做法是在存在多个合理推理路径时多次采样，再对可比较的最终答案做投票或聚合：

```text
同一问题 → 多条独立生成路径 → 提取最终答案 → 投票 / 校验 → 输出结果
```

它类似集成方法：单次随机错误可能被抵消，但成本和延迟按采样次数增长；若所有路径都基于同一个错误前提，多数投票也不会变正确。

Tree-of-Thought 则显式生成并评估多条候选路径，适合搜索、规划和创意比较。它需要一个可靠的评分或验证机制，否则只是在更大成本下生成更多文字。能用确定性程序、约束求解器或单元测试验证的步骤，应优先交给这些工具。

## 七、Structured Output：让模型输出能被程序安全消费的数据

人能理解“我建议搜索 Transformer”，程序却需要稳定的字段。例如工具调用最好表达为：

```json
{
  "tool": "search",
  "query": "Transformer attention"
}
```

结构化输出的重点不是让 JSON 看起来整齐，而是把自然语言接口转换成有模式约束的数据接口。典型层次如下：

| 层次 | 手段 | 能解决什么 |
| --- | --- | --- |
| 提示层 | 明确字段、枚举、示例 | 减少格式漂移 |
| 模型/API 层 | JSON Schema、function calling、grammar constraint | 限制可生成的结构 |
| 应用层 | JSON 解析、schema 校验、业务校验 | 拒绝缺字段、越权值和不合理参数 |
| 执行层 | 权限、限额、确认与审计 | 防止错误输出直接造成外部影响 |

Grammar constraint 可以限制模型只能生成符合语法的 token 序列。例如情感分类只能取 `positive`、`negative`、`neutral`。但它只能保证结构或枚举合法，不能保证内容真实：一个字段齐全的 JSON 仍可能包含幻觉的日期或错误的搜索词。

## 八、Output Verification：格式正确不代表答案正确

LLM 工程中的验证至少分成三类：

1. **结构验证**：能否解析；字段、类型和枚举是否正确。
2. **证据与事实验证**：回答是否由给定资料支持；引用能否定位；数值是否能由程序复算。
3. **业务与安全验证**：参数是否在允许范围；工具调用是否满足权限和用户确认要求。

错误处理也应是流程的一部分。结构错误可以要求模型根据校验错误重试；证据不足时应返回“不确定”或触发检索，而不是要求模型强行补全；涉及外部写入、支付、删除或发送信息的操作，应在执行前由确定性权限规则和必要的用户确认把关。

## 九、RAG 与 Agent 中的基础 Prompt 模板

RAG 的关键不是一句“根据资料回答”，而是清楚区分证据、问题和规则：

```text
规则：只依据提供的资料作答；资料不足时明确说明。
资料：<检索片段及来源>
问题：<用户问题>
输出：<答案 + 对应引用>
```

Agent Prompt 除角色和任务外，还必须定义工具契约：可用工具、每个参数的含义、何时应该调用、何时不能调用，以及调用结果如何进入下一步。工具的真正执行权限不能只由自然语言 Prompt 决定，应在应用代码中强制实施。

## 十、本章的基础框架

```text
Prompt：明确当前上下文中的目标、证据和输出要求
Decoding：在稳定性与多样性间选择采样策略
Chain：把复杂目标拆成可观察、可验证的步骤
In-context Learning：用示例临时指定任务边界和格式
Structured Output + Verification：让 LLM 安全进入程序工作流
```

提示工程是 LLM 应用的入口，但不是全部。越靠近生产环境，决定可靠性的往往越是任务拆分、证据来源、确定性验证、工具权限和失败处理。
