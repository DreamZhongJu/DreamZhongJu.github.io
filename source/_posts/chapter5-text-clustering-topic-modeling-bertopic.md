文本分类回答的是“这段文本属于哪个预先定义的标签”；文本聚类和主题建模回答的则是“这批没有标签的文本里，自然存在什么结构”。面对数万篇论文、客服记录或企业文档时，后者往往才是第一步：先让数据自己显出群组，再决定如何命名、检索和治理。

## 一、聚类、主题建模与分类不是一回事

```text
监督分类：已有标签 → 学习文本到标签的映射
文本聚类：没有标签 → 按相似性发现文本群组
主题建模：群组或语料 → 给出“这个群组谈论什么”的可解释描述
```

聚类结果本身通常只是 `Cluster 0`、`Cluster 1` 和对应文档；主题建模还要提取关键词、代表文档或名称，让人能够理解并使用这些群组。聚类的“正确”不等于主题名称好看，主题名称好看也不等于聚类边界合理，两层需要分别检查。

| 问题 | 例子 | 是否需要标注 |
| --- | --- | --- |
| 分类 | 将邮件归为“报销”“请假”“技术支持” | 需要已有类别和训练样本，或清晰标签定义 |
| 聚类 | 从十万封邮件中发现自然形成的沟通群组 | 不需要 |
| 主题建模 | 把一个群组解释为“差旅与费用报销” | 不需要预先标签，但需要解释机制 |

## 二、为什么关键词方法不够：从 TF-IDF 到语义向量

传统文本聚类常把文档表示为词袋或 TF-IDF 向量。TF-IDF 会提高“在某篇文档中常见、在整个语料中较少见”的词的权重，适合找关键词；但它主要依赖表面词项。

```text
car / automobile / vehicle
```

这三个词语义接近、字符却完全不同。反过来，`Apple` 在水果和科技公司语境中词形相同、含义不同。只依赖词频时，前者容易被拆开，后者容易被混在一起。

Embedding 模型将整段文本编码为稠密向量，目标是让语义相近文本在向量空间中更接近：

```text
“Neural Machine Translation”
“Machine Translation with Transformer”
           ↓
语义向量的余弦相似度通常较高
```

这不意味着 Embedding “完全理解”文本。它保留什么相似性取决于训练目标、语言、领域和输入长度；在专业语料上，选择领域匹配的嵌入模型常常比更换聚类算法带来更大的提升。

## 三、现代文本聚类的典型流水线

```text
原始文本
  → Embedding：获得语义表示
  → UMAP：压缩并保留局部邻域结构
  → HDBSCAN：按密度发现群组与噪声
  → c-TF-IDF：为每个群组提取区分性关键词
  → 代表文档 / LLM：生成可读主题名称
```

这是 BERTopic 常见的实现路径，不是唯一正确路径。每一环的目标不同：Embedding 解决“语义相似吗”，降维与聚类解决“结构如何出现”，关键词和 LLM 解决“人如何读懂这个结构”。

## 四、降维：UMAP 不是为了画一张二维图

文本 Embedding 常有数百到数千维。直接在高维空间进行基于距离或密度的聚类，会面临两类问题：计算成本增加，以及“维度灾难”——高维中最近点和最远点的距离差可能缩小，邻近关系更难区分。

UMAP（Uniform Manifold Approximation and Projection）通常先构建局部近邻图，再在低维空间中尽量保留这种邻域关系。它的重点是局部结构：原空间相近的文本，在低维空间仍应彼此靠近。相比之下，PCA 主要寻找能解释最大方差的线性方向；它可能保留全局变化，却不一定保留对密度聚类重要的局部形状。

需要注意三点：

- UMAP 会改变距离结构，不能把降维后的二维图当作原始语义空间的精确地图。
- `n_neighbors` 决定更偏向局部还是更大范围的结构，`n_components` 决定给聚类器保留多少维度。
- 固定随机种子、记录模型与参数，才能让主题随批次可比较；否则结果可能因随机初始化或语料微调而漂移。

## 五、HDBSCAN：主题数未知时怎样发现群组

K-means 必须提前指定聚类数 (K)，并倾向于找到大小和形状都相近的簇。真实文本主题往往不满足这些假设：有的主题很大，有的主题很小，且一部分文档可能本来就是跨主题或信息不足的噪声。

HDBSCAN 是一种基于密度的层次聚类方法。它寻找在不同密度阈值下仍稳定存在的群组，并可以把不属于稳定群组的样本标为 `-1`（outlier）。这对探索式主题发现很有价值：与其强迫每篇文档进入一个主题，不如承认部分文本暂时没有可靠归属。

| 方法 | 是否预先指定主题数 | 对噪声的处理 | 常见适用情形 |
| --- | --- | --- | --- |
| K-means | 是 | 必须分到某一簇 | 主题数已知且分布较均衡 |
| HDBSCAN | 否 | 可标记噪声点 | 主题数未知、密度不均的探索式语料 |

`min_cluster_size` 越大，越小的主题越可能被合并或视为噪声；它不是“越小越能发现细粒度主题”这么简单，太小也会制造难以解释的碎片簇。应该结合代表文本、主题规模和稳定性来调参。

## 六、从簇到主题：c-TF-IDF 在解释，不在理解

聚类完成后，需要回答“Cluster 7 在讨论什么”。BERTopic 常将同一簇的文档拼成一个类别文档，再计算 class-based TF-IDF（c-TF-IDF）。它提高在该簇中常出现、在其他簇中少见的词的权重：

<div class="attention-formula" role="math">c-TF-IDF(term, class) = normalized term frequency in class × inverse class frequency</div>

例如一个簇的高权重词是 `Transformer`、`Attention`、`BLEU`、`Encoder` 和 `Decoder`，它很可能与神经机器翻译相关。

这里有一个重要边界：**Embedding 用于形成语义邻近，c-TF-IDF 用于展示区分性词语。** c-TF-IDF 并没有替代 Embedding 去理解同义词或上下文，它只是让人能够审计一个主题为何被这样命名。

主题解释最好至少同时查看三样东西：高权重关键词、若干代表文档、以及簇的规模。仅凭 LLM 给出的一个漂亮名称，很容易把混杂簇误认为定义清晰的主题。

## 七、LLM 在 BERTopic 中的位置：命名与总结，而非替代聚类

LLM 可以根据关键词和代表文档生成更自然的主题名，例如把 `Transformer / BLEU / Encoder / Decoder` 命名为“基于 Transformer 的神经机器翻译”。它还能写出主题摘要、合并相近主题的说明，或协助人工审核。

但 LLM 不应遮住聚类证据。一个可靠的工作流是：先固定可复现的 Embedding、降维和聚类结果；再将关键词与代表文档交给 LLM 命名；最后保留 LLM 输入、版本和输出，允许人工改名。这样“数据结构”和“语言化解释”可以独立追溯。

## 八、BERTopic、RAG 与 GraphRAG：相通之处和边界

三者都试图让大量非结构化文本变得更可组织，但处理对象和输出不同：

```text
BERTopic：文档 → 向量空间 → 主题簇 → 主题摘要
RAG：     文档 → 切分/向量索引 → 按查询检索片段 → 回答
GraphRAG：文本 → 实体/关系图 → 社区或子图 → 图检索与全局总结
```

BERTopic 可以为 RAG 提供主题级索引、路由标签或知识库清理视图。例如先识别“产品文档”“技术文档”“业务流程”主题，再让查询在对应主题中优先检索。它不能自动解决事实溯源、chunk 粒度、更新同步或检索召回问题。

GraphRAG 的社区发现与主题聚类在“发现隐藏结构”上相似，但 GraphRAG 的基本单元是实体和关系，能表达“谁与谁以何种关系相连”；BERTopic 的基本单元是文档语义相似性。一个主题簇不等同于一张知识图谱社区，也不能直接替代关系抽取。

## 九、在科研和知识库中的实际用法

### 1. 文献地图

对论文标题、摘要或全文片段做聚类，可以快速看到大致研究方向和边缘主题。接着应由研究者检查每个簇的代表论文、时间分布和引用关系，避免把“同一个热门术语”误判为完整研究路线。

### 2. 知识库整理

聚类可以发现重复文档、孤立文档和主题边界模糊的材料，适合在入库或清理时辅助人工制定目录与标签。长期知识库还应保存文档来源、更新时间和版本；主题标签只能作为组织索引，不能成为唯一事实来源。

### 3. Agent 记忆治理

历史记录的聚类可用于发现反复出现的项目、偏好和议题，并辅助归档或摘要。但“语义相近”不代表“应该合并成长期记忆”：时间、主体、权限和事实冲突仍需要单独的治理规则。

## 十、这一章的核心框架

```text
Embedding：把语义相近的文本放得更近
聚类：从无标签语料中发现稳定群组
c-TF-IDF：用区分性词语解释群组
LLM：将证据组织成可读名称和摘要
人工审核：判断主题是否可用、是否需要合并或拆分
```

BERTopic 不是一个“让 LLM 自动懂主题”的黑箱，而是一条将神经表示、降维、密度聚类、统计解释和语言生成各司其职的流水线。理解这些边界，才能在主题稳定性、可解释性和维护成本之间做出合适取舍。
