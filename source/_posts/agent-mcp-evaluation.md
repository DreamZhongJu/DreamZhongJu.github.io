Agent 的能力上限，很大程度上取决于工具数量和质量。但每加一个工具就写一遍"连接外部 API + 解析返回 + 注册进框架"的样板代码，很快会变成维护噩梦。这篇文章讲两件事：怎么用 MCP 让工具"即插即用"，以及怎么用可观测性和评测闭环让 Agent 的能力"可衡量"。

## MCP 是什么

MCP（Model Context Protocol）是一个开放协议，把"外部能力"统一成"工具列表"暴露给 LLM 应用：

- **MCP Server**：能力的提供方。比如一个 GitHub server 暴露"查 issue、看仓库"的工具；一个文件系统 server 暴露"读写文件"的工具。
- **MCP Client**：LLM 应用这一侧。连接 server、发现工具、按需调用。

## 动态工具注册

我们的 Agent 启动时读取 `mcp_servers.json`，为每个启用的 server 做三件事：

1. **发现**：连接 server，拉取工具列表（名称、描述、输入 schema）。
2. **转换**：把每个工具的 JSON Schema 输入转成 Pydantic 参数模型，再包装成 LangChain 工具。
3. **注册**：把工具并入 Agent 的可调用集合，模型在下一轮推理时就能看到并调用它们。

配置示例：

```json
{
  "servers": [
    {"name": "exa", "transport": "streamable_http", "url": "https://mcp.exa.ai/mcp", "enabled": true},
    {"name": "filesystem", "transport": "stdio", "command": "npx",
     "args": ["-y", "@modelcontextprotocol/server-filesystem", "C:/data"], "enabled": true}
  ]
}
```

支持两种传输：`stdio`（本地子进程）和 `streamable_http`（远程服务）。配置在启动时逐条校验，无效 server 跳过并给出明确原因，不影响内置工具。

一个务实的取舍：目前每次工具调用都新建连接（`asyncio.run` 包一层），个人项目可以接受；如果要做成常驻服务，应该维护连接池。

## 可观测性：让每次请求可回溯

工具变多之后，问题定位会变难，所以配套做了请求级可观测性：每次请求记录问题（脱敏）、工具调用链、prompt/completion token、耗时、状态和错误类型，存进 SQLite。

Web 面板提供四个页面：

- **仪表盘**：请求量、成功率、今日失败、平均耗时、Token 消耗、估算成本、近 7 天趋势、工具调用排行（含失败数）、最近失败列表。
- **请求日志**：按状态/工具筛选、分页、单条详情（工具链 + 完整问答）。
- **记忆管理**：按用户查看/删除核心与存档记忆。
- **运行状态**：模型、工具数、数据库路径等配置概览。

这些数据让"Agent 今天表现如何"从感觉变成了数字。

## 评测闭环：离线评测 + 真实请求回放 + CI

可观测性解决"发生了什么"，评测解决"做得好不好"。我们搭了三层：

1. **离线评测**：基于项目文档语料的知识问答集（含负例，验证不编造）+ 工具路由用例，DeepSeek 作为裁判模型打分。
2. **真实请求回放**：把请求日志里的真实问答转成评测样本，用裁判模型打分（相关性、完整性），把生产使用变成回归信号。
3. **CI**：GitHub Actions 在无凭据环境跑全部单测，配置 `DEEPSEEK_API_KEY` 后追加离线评测 job，防止改动引入回归。

当前结果（自建评测集）：

| 维度 | 指标 | 结果 |
| --- | --- | --- |
| 知识问答 | 平均忠实度 | 1.0 |
| 知识问答 | 上下文命中率 hit@3 | 1.0 |
| 知识问答 | 负例不编造率 | 1.0 |
| 工具路由 | Top-1 准确率 | 1.0 |

需要诚实说明：自建评测集有同源偏差（语料就是项目自己的文档），满分不代表通用能力，它更像"回归测试"而不是"能力基准"。真正的能力评估需要外部数据集交叉验证，这是后续要做的事。

## 小结

这一套做下来，Agent 的工程闭环基本完整了：MCP 让能力可扩展，可观测性让行为可回溯，评测让质量可回归。如果你也在做类似的个人 Agent 项目，我建议按这个顺序投入：**先可观测性，再评测，最后才是更多工具**——否则工具越多，越不知道自己哪里坏了。
