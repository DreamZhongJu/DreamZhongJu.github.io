# 某PVZ二游的本地服务端开发：网络请求分析方法论

## 前言

在开发本地服务端时，最核心的问题是：**客户端到底向服务器发送了什么请求？服务器应该返回什么？**

本文不讨论具体游戏的协议内容，而是分享一套通用的**网络请求分析方法论**，适用于任何需要"模拟服务端"的场景。

---

## 方法论总览

```
观察 → 拦截 → 分析 → 模拟 → 验证
  │       │       │       │       │
  │       │       │       │       └─ 验证模拟响应是否被客户端接受
  │       │       │       └───────── 构建模拟响应
  │       │       └──────────────── 分析请求格式、参数、响应格式
  │       └──────────────────────── 拦截客户端与服务器之间的流量
  └──────────────────────────────── 了解客户端在什么情况下发起请求
```

---

## 第一步：观察（Observation）

在拦截流量之前，先了解客户端的行为：

- **在什么时机发起请求？** 点击按钮时？进入新页面时？定时同步？
- **请求的域名是什么？** 配置服务器？认证服务器？游戏服务器？
- **请求的顺序是什么？** 是否有依赖关系？

这些信息可以通过**域名解析观察**和**进程网络活动监控**来获取。

### 常用工具

- `netstat` / `Get-NetTCPConnection`：查看进程的网络连接
- 路由器日志：查看 DNS 查询记录
- 游戏启动器的网络活动：观察启动时的请求序列

---

## 第二步：拦截（Interception）

### 方案一：被动抓包（Pcap）

使用网络抓包工具（如 tshark/Wireshark）在网卡层面捕获所有流量。

**优点**：
- 完全被动，不会影响网络连接
- 可以捕获到所有协议（HTTP、TCP、UDP 等）

**缺点**：
- 现代游戏几乎全部使用 HTTPS/TLS 加密，看不到请求内容
- 只能看到域名、IP、连接时间、数据包大小等元信息

**典型命令**：
```bash
# 捕获特定域名的流量
tshark -i [interface] -f "host [domain]" -w capture.pcapng
```

### 方案二：中间人代理（MITM Proxy）

使用代理工具（如 mitmproxy）作为中间人，解密 TLS 流量。

**优点**：
- 可以看到完整的请求 URL、Headers、Body
- 可以看到完整的响应状态码、Headers、Body

**缺点**：
- 需要安装自定义 CA 证书到系统信任区
- 某些游戏会使用证书固定（Certificate Pinning），导致无法解密
- 代理本身可能影响游戏连接（如长连接、WebSocket 等）

**典型命令**：
```bash
# 记录所有流量到文件
mitmdump -w capture.flows -q

# 带 Web 界面的交互式代理
mitmweb --listen-host 127.0.0.1 --listen-port 8080
```

### 方案三：URL 重定向 + 本地代理

通过修改 hosts 文件将域名指向本地服务器，本地服务器同时作为**转发代理**，将请求转发到官方服务器并记录。

**优点**：
- 不依赖系统代理设置，对游戏客户端透明
- 可以同时记录和转发

**缺点**：
- 需要处理 TLS 证书
- 修改 hosts 需要管理员权限

**架构**：
```
客户端 → hosts 重定向 → 本地 TLS 代理(:443) → 记录请求/响应 → 转发到官方服务器
```

## 第三步：分析（Analysis）

### 请求分析

拿到请求后，需要记录以下信息：

```
时间戳
请求序列号
HTTP 方法（GET/POST/PUT/DELETE）
请求 URL（路径 + 查询参数）
HTTP 版本
请求头（Content-Type、User-Agent、Cookie 等）
请求体格式（JSON、Form-URLEncoded、Protobuf、二进制）
请求体长度
```

### 响应分析

```
HTTP 状态码
响应头（Content-Type、Content-Length 等）
响应体格式和内容
响应体大小
```

### 关键字段识别

需要特别关注以下字段：

| 字段类型 | 例子 | 说明 |
|---|---|---|
| 身份标识 | token、secret、session | 用于识别用户身份 |
| 设备标识 | deviceId、deviceId2 | 用于识别设备 |
| 版本信息 | clientVersion、resVersion | 客户端版本号 |
| 时间戳 | ts、startTs | 请求时间 |
| 业务参数 | stageId、poolId、charId | 具体业务数据 |

## 第四步：模拟（Simulation）

### 构建模拟响应

根据分析结果，构建服务端响应。关键原则：

1. **格式匹配**：返回的 JSON 结构必须与客户端期望的一致
2. **字段完整**：客户端可能校验某些字段是否存在
3. **类型正确**：字符串、数字、布尔值的类型必须正确
4. **状态码正确**：正常情况下返回 200，错误时返回 4xx/5xx

### 增量开发

不要一开始就试图实现完整的响应。采用**增量开发**策略：

```
1. 先返回空成功响应 {}（确认路由正确）
2. 再添加必要的字段（确认客户端能解析）
3. 再完善业务逻辑（确认功能正常）
4. 最后优化性能和数据一致性
```

---

## 第五步：验证（Verification）

### 客户端行为分类

观察客户端在收到响应后的行为，可以判断响应的正确性：

| 客户端行为 | 含义 |
|---|---|
| 继续下一个请求 | ✅ 响应被接受 |
| 重复相同的请求 | ⚠️ 响应可能不被接受 |
| 弹出错误提示 | ❌ 响应格式错误或业务逻辑错误 |
| 网络异常提示 | ❌ 连接问题或响应解析失败 |
| 数据已更新/同步提示 | ⚠️ 客户端检测到数据不一致 |
| 退出登录 | ❌ 严重错误，session 无效 |

### 错误码分析

客户端通常会显示错误码，这些错误码可以帮助定位问题：

| 常见错误码 | 可能原因 |
|---|---|
| 500 | 服务端异常（代码错误、空指针等） |
| 404 | 请求的端点不存在 |
| 410 | 登录失败 / 连接被拒绝 |
| 400 | 请求参数错误 |
| 200 + 业务错误码 | 业务逻辑错误（如"合成玉不足"） |

## 实际案例：某塔防游戏的请求序列

下面是一个经过脱敏处理的请求序列示例，展示了客户端从启动到进入主界面的完整流程：

### 阶段一：启动器配置

```
1. 获取启动器版本信息
2. 获取游戏配置（服务器列表、CDN 地址等）
```

### 阶段二：游戏配置

```
3. 获取游戏版本（resVersion、clientVersion）
4. 获取 SDK 应用配置（支付方式、协议 URL 等）
5. 获取服务器时间
```

### 阶段三：用户认证

```
6. 获取用户基本信息（需要 token）
7. OAuth2 授权（获取授权码）
8. U8 SDK token 交换（获取游戏 session）
9. 获取协议版本（用户协议）
10. 登录（建立游戏 session）
11. 同步角色数据（SyncData）
```

### 阶段四：游戏内

```
12. 获取未完成订单
13. 同步各种状态（定时心跳）
14. 签到
15. 同步抽卡状态
```

### 阶段五：战斗

```
16. 编队调整
17. 开始战斗
18. 战斗结算（获取奖励、解锁关卡）
19. 保存战斗回放
```

## 常见问题与解决方案

### TLS 证书问题

**问题**：中间人代理的证书不被游戏客户端信任。

**解决方案**：
1. 将代理的 CA 证书安装到系统信任区
2. 使用 `--ssl-insecure` 参数（不推荐，客户端可能报错）
3. 先测试客户端是否使用证书固定（Certificate Pinning）

### 长连接问题

**问题**：游戏客户端使用 WebSocket 或 TCP 长连接，代理无法正确处理。

**解决方案**：
1. 使用被动抓包（Pcap）观察连接行为
2. 在本地服务器中实现对应的长连接处理
3. 或者让长连接直连官方服务器（通过 ProxyOverride 排除）

### 请求体大小问题

**问题**：POST 请求体较大（如战斗回放可达 10KB+），代理读取不完整。

**解决方案**：
1. 根据 Content-Length 头读取完整请求体
2. 不要使用 `read(65536)` 一次性读取，而是循环读取直到满足 Content-Length

---

## 总结

网络请求分析是本地服务端开发中最关键的一步。本文介绍的"观察 → 拦截 → 分析 → 模拟 → 验证"五步法，可以应用于任何游戏的本地服务端开发。

记住几个关键原则：
1. **先看后动**：不要猜测客户端的行为，通过抓包确认
2. **增量迭代**：从空响应开始，逐步完善
3. **格式准确**：客户端的解析器是严格的，任何字段的缺失或类型错误都可能导致失败
4. **安全第一**：在分析过程中，不要向官方服务器发送恶意请求，不要修改客户端文件
