## TL;DR

LLM 从群聊里抽实体抽得很起劲，但它不知道「cherry」「东北雨姐」「FoldedCherry」是同一个人。灌完两个群后，我的知识图谱里 7,997 个实体中**人名实体的重复率高得离谱**——一个人平均 2~3 个节点，社交枢纽级别的群友能有 9 个。

这篇记录 Kairós 的身份对齐三轨制：

1. **canonical `qq:<uid>` 锚点**——能拿到 QQ 号的实体一律锚定；
2. **nickmap 自动反查**——collector 记录的"昵称→QQ"映射做批量归一；
3. **人工共指注册表**——`coref_overrides.json` 里一行一个别名，`coref.merge_entity()` 迁移边。

以及一个价值连城的教训：`merge_entity` 会把目标节点的名字覆盖成源节点的名字，批量合并后我朋友的"本体"一度改名成了一个梗。

## 一、问题：抽取器眼中的平行宇宙

LLM 抽取是按窗口独立进行的。同一个窗口里「康哥」在说话，实体表里就有「AAA木头收藏康哥」；下个窗口他改了群名片叫「梦终剧」，就又多出一个新实体。两边没有任何机制知道这是同一个人。

后果在图算法里被放大：算度数枢纽时，「我」被劈成了 9 个节点各拿一份边；做推理链挖掘时，经过"我"的两跳路径因为中间节点分裂而全部断掉。**不对齐身份，后面一切都是空中楼阁。**

## 二、第一轨：canonical 锚点

设计原则只有一条：**凡是能确定 QQ 号的实体，canonical 字段一律写成 `qq:<uid>`，名字只是显示标签。**

```sql
UPDATE entities SET canonical='qq:792059284' WHERE name IN
  ('梦时空','AAA木头收藏康哥','梦终剧','蓬莱终剧', ...);
```

这样"同名不同人"（两个都叫小师的）和"异名同人"（cherry=东北雨姐）都有了统一的裁决标准：看锚点，不看字符串。

collector 插件在日常收消息时顺手维护一张 `nickmap.json`（昵称 → QQ），这是锚点的来源。它有个隐藏福利：**反查**。想知道某个 QQ 用过哪些历史昵称，一行字典推导就出来——后来排查"这个实体到底是谁"全靠它。

## 三、第二轨：自动归一的边界

有了 nickmap，理论上可以全自动合并：所有昵称解析到同一 uid 的实体，canonical 统一，完事。

但实践中我只让自动化做到"归一 canonical"，**不做边的迁移**。原因是一个真实案例：群里有人长期挂着「XX（恩师 姓余.）」这种带后缀的名字，抽取器把它当成了完整人名建了实体，同时另一个窗口里裸名「XX」也建了实体。两者 nickmap 都指向同一 uid，自动合并没问题——

但如果昵称映射本身有歧义呢？群里真实存在三个都带"小刘"字样的不同的人，用户明确告诉我"不用合并"。**自动化的边界必须由人工可审计的配置来兜底**，这就是第三轨存在的意义。

## 四、第三轨：人工共指注册表 + merge_entity

`data/coref_overrides.json` 长这样：

```json
{
  "cherry": "qq:2654526702",
  "Cherry": "qq:2654526702",
  "cherry（恩师 姓余.）": "qq:2654526702",
  "FoldedCherry": "qq:2654526702"
}
```

查询侧先查这张表再走默认归一；合并侧调用 `coref.merge_entity(old_id, target_id)`，把 old 的所有关系边改指向 target，然后删掉空壳。

### 坑：名字会被源节点覆盖

`merge_entity` 的实现里有一句"顺手"的逻辑：把 target 的 name 更新为更"常用"的那个。判断标准简单粗暴——谁边多听谁的。结果我做批量合并时，主实体（3000+ 边）被一个梗名（当时恰好边更多）顶掉了，本人看了沉默，我看了想删库。

修复后的纪律：**任何一次 merge 之后，立刻显式 UPDATE 回权威名**：

```python
rep = coref.merge_entity(old_id, target_id)
con.execute("UPDATE entities SET name=? WHERE id=?", (authoritative_name, target_id))
```

听起来蠢，但比把"常用名推断"写聪明便宜得多——身份对齐这种事，确定性永远优先于启发式。

## 五、实战：一场九马甲归宗

以一位群友为例，最终合并进 `qq:2654526702` 的实体清单：

```text
cherry(76边) + cherry（恩师 姓余.）×2种标点(101边) + Cherry(1)
+ Foldedcherry + FoldedCherry
```

合并前这 6 个节点各自为战，度数最高的也才 135；合并后主实体从 772 条边涨到 **945 条**，直接跃升全库第四大枢纽。更有意思的是合并的"涌现效应"：cherry 名下的「位于武汉」「参加高考数学」「脏增肌」全部并入了主实体画像——一个只看「东北雨姐」节点永远看不到的立体人设出现了。

同时去重逻辑干掉了 110 条自言自语边（合并前存在「雨姐提及cherry」「cherry回复雨姐」这类实际上是同一人自说自话的关系）。**身份对齐不只是加边，更重要的是消灭假边。**

## 六、隐私红线

对齐做得越狠，画像越完整，隐私风险越高。Kairós 的做法：

- 真实姓名类实体在入库时就地掩码（`许**`/`邓**` 形式），掩码形态参与一切后续处理，合并操作不得"还原"它们；
- 共指注册表里虽然存了别名到 QQ 的映射，但这份文件不出服务器，也不进入任何 LLM 的上下文；
- 对外暴露的 API 只返回实体 id 和掩码名。

## 结语

身份对齐没有高深算法，全是工程判断：什么时候信机器、什么时候停下来等人拍板、出了错怎么兜底。目前这套三轨制支撑着 7,997 实体的图谱稳定运行，人工共指表总共也就二十几行——**好的自动化不是替代人工，而是把人工决策压缩到最少且最关键的位置上**。
