# 某PVZ二游的本地服务端架构对比分析

## 前言

最近在研究某款二次元塔防游戏的本地服务端实现，接触了两个开源项目：一个基于 Java Spring Boot，一个基于 Python FastAPI。本文从技术角度对比它们的架构设计、功能完成度和实现思路。

**声明**：本文仅分析开源项目的代码实现，不涉及对官方服务器的逆向工程或网络抓包。所有数据均来自公开的 GitHub 仓库。

---

## 项目概览

| 维度 | 项目 A | 项目 B |
|---|---|---|
| 语言 | Java 17 (Spring Boot) | Python 3.12 (FastAPI) |
| 数据存储 | MySQL 8.0（必须） | 文件 JSON（可选 PostgreSQL） |
| 部署难度 | 较高 | 较低 |
| 代码可读性 | 一般 | 较好 |
| 社区活跃度 | 较高 | 较新 |

两个项目都实现了"拦截游戏客户端网络请求 → 重定向到本地服务器 → 返回模拟响应"的架构。

---

## 架构设计对比

### 项目 A：单体应用 + 数据库

项目 A 采用典型的 Spring Boot 单体架构，所有服务（Config、Auth、Game）集中在同一个进程中，通过不同的 URL 路由区分。

```
客户端 → TLS 代理(:443) → HTTP 转发 → 项目 A(:31416) → MySQL(:3306)
```

优点：
- 架构简单，一个进程搞定所有
- 数据库持久化，数据不丢失

缺点：
- 过度依赖数据库，启动慢
- 代码耦合度高，不同模块互相引用

### 项目 B：路由分离 + 文件存储

项目 B 采用 FastAPI 的 APIRouter 机制，按功能模块划分蓝图。

```
客户端 → TLS 代理(:443) → HTTP 转发 → 项目 B(:8443) → JSON 文件
```

每个模块独立一个文件（bp_account.py、bp_gacha.py、bp_rlv2.py 等），代码组织清晰。

优点：
- 模块解耦，易于扩展
- 默认文件存储，无需数据库

缺点：
- 文件存储在高并发下性能可能不足
- 项目较新，部分功能未完成

## 抽卡系统实现分析

两个项目的抽卡实现都分为两层：

### 1. 卡池配置层

定义每个卡池包含哪些干员、各稀有度的概率：

```json
{
  "perAvailList": [
    {"rarityRank": 5, "charIdList": ["char_001", "char_002", ...], "totalPercent": 0.02},
    {"rarityRank": 4, "charIdList": ["char_003", "char_004", ...], "totalPercent": 0.08}
  ]
}
```

### 2. 抽卡逻辑层

实现概率计算、保底机制、潜能返还等逻辑。

**项目 A** 的抽卡逻辑在 `gacha.java` 中，约 500 行，包含：
- 单抽 / 十连
- 保底计数（50 抽后概率递增）
- 重复干员转化为潜能 + 黄票

**项目 B** 的抽卡逻辑更复杂，使用了**策略模式**（Strategy Pattern）：
- `AdvancedGachaBasicManager`：基础类，定义抽卡流程
- `AdvancedGachaSimpleManager`：标准池实现
- `AdvancedGachaNormalManager`：常规寻访
- `AdvancedGachaLimitedManager`：限定寻访
- `AdvancedGachaNewbeeManager`：新手寻访
- `AdvancedGachaDoubleManager`：双UP池

每个管理器可以独立覆盖概率计算、保底机制和卡池详情返回。

## 肉鸽系统实现分析

肉鸽（Roguelike）是游戏中最复杂的玩法之一。项目 B 实现了部分端点，但仍有大量缺失。

### 客户端期望的请求序列

```
1. 创建游戏 → 选择主题/难度
2. 选择初始干员 → 选择初始遗物
3. 移动 → 遭遇事件/战斗
4. 招募干员 → 购买道具
5. 战斗结算 → 获得奖励
6. 循环直到通关/失败
```

### 实现的端点

项目 B 实现了 `createGame`、`chooseInitialRecruitSet`、`chooseInitialRelic`、`moveTo`、`recruitChar`、`battleFinish` 等核心流程，约 15 个端点。

### 缺失的端点（43 个）

包括炼金术、银行存取、骰子选择、远征选择、游戏结算、刷新商店等。这些功能在客户端中对应不同的 UI 交互，但服务端尚未实现对应的处理逻辑。

## 战斗系统的问题

两个项目的战斗系统都存在共同问题：**掉落奖励的解析逻辑与游戏实际数据格式不匹配**。

游戏数据中的掉落类型（`dropType`）和掉落概率（`occPercent`）是字符串枚举值：

```
dropType: "ONCE" | "NORMAL" | "ADDITIONAL" | "COMPLETE"
occPercent: "ALWAYS" | "SOMETIMES"
```

但服务端代码错误地使用 `getIntValue()` 解析，导致 `NumberFormatException`。

修复方式：建立字符串到整数的映射表，将枚举值转换为对应的内部编码。

---

## 总结

两个项目各有优劣：

- **项目 A** 适合想快速体验游戏核心功能的用户，战斗系统有实现但需修复
- **项目 B** 功能更完备（肉鸽/卫戍/社交均有模块），Python 生态更易修改

对于想深入了解游戏服务端实现的人来说，分析这两个项目的代码是一个很好的学习路径。
