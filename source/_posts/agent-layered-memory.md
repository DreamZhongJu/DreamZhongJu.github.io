Agent 的一个老问题是"没有记忆"。我做的飞书研究助手早期接了 Claude-Mem 做对话级记忆，但很快发现它不够：Claude-Mem 存的是原始对话观察（observations），越多越杂，既没有分层也没有治理。后来参考 mem0 和 Letta（MemGPT）的思路，把记忆重构成两层治理。这篇文章记录落地过程。

## 先想清楚：要存什么，谁来存

把记忆拆成两类，职责完全不同：

| 类型 | 内容 | 谁来写 | 怎么读 |
| --- | --- | --- | --- |
| 对话观察 | 一次对话的原始记录 | Claude-Mem（可选外部服务） | 语义搜索召回 |
| 长期事实 | 提炼后的稳定信息（偏好、方向、决定） | 本地 LLM 提取 + 治理 | 分层 + 相关性 |

关键决策是：**本地长期事实表才做治理**，Claude-Mem 继续当"原始记忆仓库"。这样两边各司其职，不会互相污染。

## 两层记忆：核心 vs 存档

参考 Letta 的 core memory / archival memory 分层：

- **核心记忆**：用户长期身份与核心偏好（姓名、研究方向、重要偏好）。每次请求无条件加载，数量严格控制（每用户 8 条），超出自动修剪最旧的。
- **存档记忆**：项目、习惯、决定等可检索事实。按相关性召回，每用户 120 条，按最近访问时间清理。

读取时拼接顺序是：核心记忆 -> 相关存档 -> 对话观察。

## 操作治理：add / update / delete / noop

早期版本用"内容哈希"去重：同样的话不会重复插入，但"喜欢喝咖啡"和"喜欢喝美式咖啡"会变成两条。mem0 的做法是让模型输出显式操作，我照搬了这个思路：

```json
{
  "ops": [
    {"op": "add", "category": "研究", "is_core": true, "content": "研究方向是知识图谱增强的RAG"},
    {"op": "update", "target_id": "abc123", "category": "研究", "content": "研究方向是KG-RAG与AI Agent"},
    {"op": "delete", "target_id": "abc123"},
    {"op": "noop"}
  ]
}
```

提取节点把"用户已有记忆摘要 + 当前消息"交给模型，模型判断是新增、合并更新、删除还是忽略。于是同一事实只会有一条记忆，内容变化时原地更新，用户说"忘记 XX"时真正删除。

## 预算与遗忘

光有操作还不够，记忆必须有限度：

- 核心记忆超 8 条：按更新时间修剪最旧的。
- 存档记忆超 120 条：按 `last_accessed_at`（最近访问时间）清理最久没被用过的。
- 每次召回都会更新访问次数和时间，为遗忘策略提供依据。

一个细节：同一批写入的记忆时间戳可能完全相同，单纯按时间排序会删错条目——我加了 `rowid` 作为并列排序的次级键才稳定。

## 隐私与安全

记忆是敏感数据，落地时做了几件事：

- 写入前过滤密钥、密码、授权码等模式。
- 记忆按用户范围隔离（owner 哈希，不直接暴露飞书 ID）。
- 提供全量清空和单条删除接口（面板上可操作）。

## 效果与局限

重构后最直观的变化：记忆不再无限膨胀、同一事实不会重复、用户明确遗忘的信息真的会被删掉。离线评测里，工具路由和记忆相关场景的行为保持稳定。

局限也要说清楚：

- 没有 embedding，冲突判断和相似召回依赖 LLM 判断，成本比向量检索高，规模大了会吃力。
- 提取质量取决于模型；模型偶发输出非法 JSON 时，我们选择静默跳过而不是写坏数据。
- "记忆是否该记住"本身有主观性，目前的过滤规则是保守的（宁可不记，不记错）。

如果你也在给 Agent 加记忆，我的建议是：**先定好"存什么、谁来存、存多久"，再动手写表结构**。记忆治理的本质不是存储技术，而是信息生命周期管理。
