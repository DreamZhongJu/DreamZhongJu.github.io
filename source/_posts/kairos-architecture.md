几个月前我开始做一个自托管的飞书研究助手，给它起名叫 Kairós（凯伊）。现在它已经从一个"能联网搜索的飞书 Bot"变成了一个有 25 个工具、知识图谱、技能系统、日报/周报/月报、反馈闭环、MCP 服务的个人情报平台。这篇文章复盘它的完整架构和工程演进。

GitHub 仓库：[DreamZhongJu/kairos-intel](https://github.com/DreamZhongJu/kairos-intel)，欢迎 Star。

## 架构总览

他是用 Python + LangGraph 搭的，核心是一个"消息→Agent→工具→回答"的循环。25 个注册工具涵盖了搜索、论文、GitHub、飞书文档、知识库、记忆、知识图谱、技能加载等。飞书 WS 长连接作为主入口，同时暴露了 MCP 和 OpenAPI 两套外部接口。

日报/周报/月报走 APScheduler 定时触发，汇总后经飞书大脑通道推送。所有数据（记忆、日志、反馈、知识图谱）都落在 SQLite 里，不依赖外部数据库。

## 能力一览

### 对话式研究
- 飞书私聊 / 群聊，25 个工具 LangGraph 自主编排
- 回答带**可校验的引用来源**（从工具链提取，不靠 LLM 自报）
- 长回答**分段发送 + 占位进度**，多模型按复杂度路由

### 情报日报
- 每日 09:00（社会/科技/开源/研究/新技术/团队 + GitHub Trending）
- 每周一 09:05 周报 / 每月 1 日 09:10 月报
- 飞书大脑通道推送

### 知识管理
- 分层长期记忆（核心 / 存档，SQLite 自动提取去重）
- **本地知识图谱**：零向量模型，FTS5 关键词 + 实体关系图
- 62 个外部研究技能按需加载

### 开放接口
- MCP 服务（11 工具，给外部 AI 客户端调用）
- OpenAPI REST（/api/chat /api/tools /api/reports /api/knowledge/stats）
- 多 Provider 模型支持

### 质量与观测
- Web 面板（仪表盘 / 日志 / 记忆 / 运行状态）
- 79 个单元测试 + CI 全绿
- 反馈闭环（👍/👎 入库，差评可回溯复测）
- 离线评测套件（honesty / relevancy / 工具路由）

## 四个关键设计

### 1. 引用来源：从工具链提取，不靠 LLM 自报

LLM 经常会"忘记"或编造来源。我的做法是在运行时从真实工具消息链里提取 URL——搜索结果的 JSON 字段、ead_webpage 的入参就是原文链接、纯文本兜底扫描。然后让模型在这个集合里自选引用，运行时校验只保留真实出现在工具输出中的 URL。脚注里的每个链接都是工具真的返回过的。

### 2. 本地知识图谱：不做向量，只用 FTS5 + 图

我没有用向量数据库（嵌入模型需要另外配 API），而是用 SQLite 的 FTS5（trigram 分词，中文子串匹配）做关键词检索，加 LLM 从文档抽取实体/关系三元组存 SQLite 图，查询时用 SQL 做 1-2 跳邻域遍历。个人规模完全够用。

### 3. 技能系统：开放接口，不进仓库

62 个研究技能（文献综述、论文润色、实验设计……）不进 Git 仓库。用纯标准库写了一个 HTTP 技能读取服务，凯伊通过 skill_list 和 skill_load 两个工具按需加载。接入方式就是配一个 SKILL_API_URL 环境变量。

### 4. 反馈闭环：让生产数据驱动优化

每次回答自动记录到 feedback 表，每个回复消息 ID 关联到对应回答。用户在飞书里对回答点 👍/👎 时，WS 反应事件被捕获，通过 SQLite 的 json_each 匹配到消息行，更新计数。差评回答可随时拉取用于回归评测。

## 工程踩坑

- **CI 0 个 job**：if: 里不能引用 secrets 上下文（GitHub 安全限制），改成 shell 检查环境变量
- **模块级 uild_client() 在无 key 时导入崩溃**：新版 SDK 对空 key 抛异常，全线改成 uild_client_optional() + None 保护
- **Python 3.11 的 f-string 限制**：\' 转义在 3.11 的表达式里是语法错误，本地 3.12+ 掩盖了
- **飞书长回答**：按段落边界 ≤1600 字分段发送，发完撤回占位
